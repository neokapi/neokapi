# The loop in CI

Every merge changes source content, and its translations, terms and voice
checks fall behind. CI can catch them up on every change or on a schedule with
[the kapi loop](/the-loop). Items a machine cannot decide **wait for review**
in the team's review session on the server, and the ship gate protects
releases. An ordinary build passes while target languages are behind.

On a project connected to a Bowrain server, a CI run of `kapi up` executes on
the **server venue**. The job pushes the drift, the server runs the loop with
the organization's AI keys, shared content memory and terms, and the results
come back to the working tree. The runner holds a server token and no
provider keys.

The sections below list the CI surfaces and the exit codes they share. The kapi
site has the step-by-step walkthroughs for scheduling, gating and cost
reporting on GitHub and GitLab:

## The contract

A pipeline needs three commands and their exit codes:

| Command | Role | Exit behavior |
|---|---|---|
| `kapi status` | **Observe**: per-locale coverage and gate standing | Always `0`: behind is pending work, not an error |
| `kapi up` | **Produce**: runs the kapi loop | `0` whether the run caught everything up, left work waiting for review, or went on after the event stream ended early; non-zero when the run broke or its outcome is unknown |
| `kapi check --ship` | **Enforce**: the release bar | `0` pass, `3` gate unmet, `4` a gate did not run, `1` operational error |

Work waiting for review exits `0`. Add the gate to merge-request pipelines and
a quality regression cannot merge. Day-to-day drift goes to review, and builds
keep passing.

## The surfaces

| Surface | How it runs | Guide |
|---|---|---|
| GitHub Actions | [`setup-kapi`](https://github.com/neokapi/setup-kapi) installs the CLI (the bowrain plugin included by default); [`kapi-action`](https://github.com/neokapi/kapi-action) runs `kapi up` and reports what changed, and a step of your own commits it or opens a pull request. The reusable [`kapi-workflows`](https://github.com/neokapi/kapi-workflows) (`up.yml@v1`, `gate.yml@v1`) compose both into one-line jobs | [GitHub Actions](/cli/use-cases/github-actions) |
| GitLab CI | [`kapi-components`](https://gitlab.com/neokapi/kapi-components) from the CI/CD Catalog: `up` runs `kapi up` and reports what changed, and with `deliver: mr` opens a merge request; `check` gates merge-request pipelines | [GitLab CI](/cli/ci/gitlab) |
| Any container runner | `ghcr.io/neokapi/kapi` (cosign-signed; the server-sync plugin is preinstalled, so `kapi up` / `push` / `pull` work out of the box) and the CLI directly; the exit codes above are the contract | this page |
| No pipeline | The forge connector / Bowrain GitHub App: the server converges on every push to the tracked branch and delivers the results back as one PR/MR | [The Bowrain GitHub App](/cli/ci/github-app) |

## Which to use when

- **You own the repository's CI** and want control over triggers, delivery and
  gating: use `kapi-action` on GitHub or `kapi-components` on GitLab. Each job
  is an ordinary pipeline step you can shape.
- **You want minimal setup on GitHub**: the reusable workflows give you the
  whole produce-and-deliver or gate job as a single `uses:` line.
- **Nobody owns the repository's CI**, as in a docs, marketing or content
  repository, or you want no configuration in the repository: connect it
  server-side with the [forge connector or the Bowrain GitHub App](/cli/ci/github-app).
  The server catches up on every push and delivers a pull request back.

## Authenticating a runner

Mint a CI token once, from an authenticated machine:

```bash
kapi auth login
kapi auth token create --name "ci" --expire-days 90
```

The token (`bwt_…`) is shown once, so store it as a CI secret right away. On
the runner, `BOWRAIN_AUTH_TOKEN` carries the credential, and the CLI checks
it before any stored login:

```bash
BOWRAIN_AUTH_TOKEN=bwt_...
BOWRAIN_SERVER_URL=https://bowrain.example.com   # self-hosted only
```

You need `BOWRAIN_SERVER_URL` only for a **self-hosted** server. The hosted
service (`https://app.bowrain.cloud`) is the built-in default, and project
commands (`kapi up`, `push`, `pull`, `check`) read the server from the
checked-out recipe's `bowrain:` block. On GitHub Actions,
`setup-kapi`'s `auth-token` and `server` inputs export exactly these two
variables. On GitLab, set them as masked CI/CD variables. List and revoke
tokens with `kapi auth token list` and `kapi auth token delete`.

What a job needs beyond the server token depends on its venue:

- **Server venue** (a connected project): nothing. The server holds the AI
  keys; the job only pushes, watches, and pulls.
- **Local venue** (`kapi up --local`, or a project with no `bowrain:` block):
  the loop runs inside the job and needs a provider key, for example
  `ANTHROPIC_API_KEY`, as a CI secret.
- **Gate-only jobs**: `kapi check --ship` reads the working tree and needs
  no AI keys; when the gate enforces governed terms, the job runs
  `kapi pull` first and needs the server token. See
  [Gate governed terms in CI](/cli/use-cases/brand-terminology-ci).
