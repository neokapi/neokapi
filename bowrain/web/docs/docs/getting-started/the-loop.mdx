# The kapi loop on Bowrain

Your source content changed. Its translations, its terminology, its brand
conformance are now behind — and that is normal, not an error. Kapi treats
catching up as the everyday state of a shipping project and gives it one verb,
**`kapi up`**: reuse what you've translated before, AI-translate the rest,
check everything produced, and **park** what a machine cannot decide for a
person. That cycle is **the kapi loop**.

Bowrain is where the loop runs *hosted*. On a project whose recipe declares a
`server:` block, the same `kapi up` executes on your Bowrain server — the
organization's AI keys, the shared translation memory, terminology, and
brand checks — and what it parks lands in the team's review queue instead of a
solo worklist. Content that never touches a checkout converges the same way:
a [connector](/server/connectors) pulls it in server-side, and the loop catches
it up where it lives.

This page covers what Bowrain adds to the loop. The model itself — the
lifecycle ladders, coverage gates, and approver classes — is documented once,
on the kapi site:
<KapiLink to="/kapi/convergence">The kapi loop</KapiLink>.

## Three roles, three surfaces

The loop keeps producing, promoting, and releasing separate. On a connected
project, each role has a home:

/>

- **The loop produces.** `kapi up` — or a push under the `server.converge`
  policy, or a server-side flow on connector content — drives every unit as far
  up its lifecycle as a flow can take it unaided.
- **Review promotes.** What the loop parks appears in the project's
  [Review surface](/server/review), where a person (or several — decisions are
  shared) advances a unit past what a machine can decide.
- **The gate releases.** [`kapi check --ship`](/cli/use-cases/brand-terminology-ci)
  answers one question — *is this scope shippable?* — and is the explicit,
  opt-in enforcement point for a release. Target-language drift never fails an
  ordinary build.

:::note[The formal name]
The model behind the loop — derived state, lifecycle ladders, coverage gates —
is formally called **convergence**; the server-side runs are *convergence as a
service* ([AD-022](/architecture-decisions/022-convergence-as-a-service)). The
REST API, the run event stream, and `--json` output keep that vocabulary; these
pages say *the loop*.
:::

## Source first: settle before the fan-out

The loop does not translate on push and hope. It **settles the source first**,
holds at a source ship-gate until the source is ready, and only then translates
the *approved* source per locale — because source content is shared across every
language, so a term left unresolved or a sentence left off-brand would be paid
for once per language, then paid for again when the source is fixed and
everything retranslates. Settling once, in front of the fan-out, is the seam
between the loop's automatic pass and governed review: the source-readiness
gate is where a person signs off before the loop pays the per-language cost.

- **Settle the source.** A server run's first pass runs the source stage over the
  source locale only — source checks, do-not-translate terms marked and
  **protected** so translation can never touch them, source QA — and stamps each
  unit's source status up the authoring ladder (*authored → checked → approved*).
- **Hold at the source ship-gate.** The project's `source_gate`
  ([`defaults.source_gate`](/architecture-decisions/022-convergence-as-a-service),
  default `checked`) is the source-side counterpart of the ship gate. Source that
  has not cleared its bar **holds**: the run parks with the reason
  `source_not_ready`, opens a **source-review task** in the team's queue (see
  [Review](/server/review)), and reports how many blocks are blocked on source —
  it never burns AI translating content you are about to change. A project that
  genuinely wants raw fan-out sets `source_gate: none` to opt out.
- **Translate only the approved source.** Settled source fans out per locale,
  TM-first — recycle what the shared memory already has, AI-translate the
  remainder, check what was produced. Protected terms stay protected through the
  model.
- **Hold at the target ship-gate.** A locale that clears its `ship_gate` is
  shippable; whatever a machine cannot decide **parks** for review rather than
  shipping under-reviewed.

This is the venue's differentiator: everyone else does source → machine
translation → N locales; Bowrain gates on source readiness *before* the fan-out.
Editing a source unit re-opens the source gate for only the changed segments, so
a fix re-settles and re-translates just those, never the whole corpus. The model
itself — the ladders and gate thresholds — is documented once on the kapi site:
<KapiLink to="/kapi/convergence#source-first">Source first</KapiLink>.

## Who starts the loop

Three starters, one loop — each suits a different way of working:

<LanesDiagram
  lanes={[
    {
      title: "A terminal",
      sub: "kapi up",
      role: "translate",
      steps: ["push the drift", "server runs the loop", "progress streams back"],
    },
    {
      title: "A push",
      sub: "server.converge: on-push",
      role: "io",
      steps: ["kapi push arrives", "the server catches up", "results wait for pull"],
    },
    {
      title: "CI or a connector",
      sub: "kapi-action · GitLab · GitHub App · sync",
      role: "qa",
      steps: ["change detected", "converge server-side", "deliver a PR / publish back"],
    },
  ]}
  caption="The same server-side loop, started from a terminal, a push policy, or an automated pipeline."
/>

- **From a terminal.** [`kapi up`](/cli/commands/up) on a connected project
  prints its resolved venue first (*server*), pushes the drift, streams the
  server run's progress live into the same terminal view, and pulls the results
  down. `kapi up --local` overrides the venue for one run — the loop executes on
  your machine and your keys, and the results are pushed so the server is never
  left stale. `kapi up --server` requires the server venue, failing rather than
  falling back (for CI that must never spend local keys).
- **From a push.** With `server.converge: on-push` on the recipe's `server:`
  block, every `kapi push` triggers a server-side run — the project stays
  continuously caught up without anyone running `up`. The policy is explicit
  and per-project, the way `git push` triggering CI is a repository policy. See
  [Automation](/server/automation).
- **From CI, or no pipeline at all.** [GitHub Actions, GitLab CI, or the
  Bowrain GitHub App](/cli/ci/overview) run the loop on a schedule or on every
  change and deliver the results as a pull request. Content connected
  server-side — a CMS, a design tool — converges without any checkout when a
  [server-side flow](/server/flows) or automation rule runs over it, and
  publishes back to where it came from.

## Seeing it

Every surface reads the same derived state:

- **In the terminal**, [`kapi status`](/cli/commands/status) shows the
  per-locale coverage grid, the server standing, and the effective venue and
  `server.converge` policy.
- **In the web and desktop app**, a project's **Runs** view lists the
  server-side runs — *Running*, *Up to date*, *Parked*, with the trigger
  (*Manual*, *kapi up*, *On push*), the pass count, and a per-locale summary
  such as "3 shippable · 1 parked". A **Run now** button starts a run from the
  app, and an in-flight run can be canceled.
- **In the review queue**, parked units are the worklist: the loop reports them
  as awaiting a person and still exits zero. Parked work is pending review, not
  an error.

A run started in a terminal and a run started from the app emit the same event
stream, so progress rendered in the CLI, the Runs view, and `--json` for agents
never disagree.
