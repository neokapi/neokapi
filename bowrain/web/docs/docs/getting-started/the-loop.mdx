# Keeping content caught up

When source content changes, translations and previous check results may need
updating. A Bowrain **run** reuses eligible content memory, drafts the remaining
text and checks the results. Work that needs a reviewer is **parked** in the
team's review queue.

Runs execute on the server using the configured AI credentials and the
workspace's shared terms, content memory and voice profiles. Content imported
through a [connector](/server/connectors) uses the same processing flow.

This page covers what happens on the server. The model itself, the lifecycle
ladders, coverage gates, and ship states, is documented once, on the kapi
site, where it is called *the kapi loop*:
<KapiLink to="/kapi/convergence">The kapi loop</KapiLink>.

## Three roles, three surfaces

Producing, promoting, and releasing stay separate. Each role has a home:

    {

      sub: "the ship gate, in CI",
      role: "qa",
      edge: "gate met",
    },
  ]}
  caption="A server run produces; review in the app promotes what a machine can't decide; the ship gate releases."
/>

- **A run produces.** A server-side flow over connector content, a push under
  the `bowrain.converge` policy, or a developer's `kapi up`: each drives every
  unit as far up its lifecycle as a flow can take it unaided.
- **Review promotes.** What a run parks appears in the project's
  [review session](/server/review), where a person (or several; decisions are
  shared) advances a unit past what a machine can decide.
- **The gate releases.** [`kapi check --ship`](/cli/use-cases/brand-terminology-ci)
  answers one question, *is this scope shippable?*, and is the explicit,
  opt-in enforcement point for a release in a pipeline. Language drift never
  fails an ordinary build.

:::note[The formal name]
The model behind this (derived state, lifecycle ladders, coverage gates) is
formally called **convergence**; the server-side runs are *convergence as a
service*. The REST API, the run event stream, and `--json` output use that
vocabulary. On the kapi site the same model is named *the kapi loop*.
:::

## Source first: settle before the fan-out

A run **settles the source first**: it checks source content and waits until it
meets the configured source gate before translating it. Resolving source issues
before translation avoids repeating corrections in each target language.
The gate can require human approval when the project needs it.

  caption="A server run settles the source, holds at the source ship-gate until it clears, then translates source that meets the configured gate. Work that needs review is added to the review queue."
/>

- **Settle the source.** A server run's first pass runs the source stage over the
  source locale only (source checks, do-not-translate terms marked and
  **protected** so translation can never touch them, the rule-based checks) and stamps each
  unit's source status up the authoring ladder (*authored → checked → approved*).
- **Hold at the source ship-gate.** The project's `source_gate`
  (`defaults.source_gate`, default `checked`) is the source-side counterpart of
  the ship gate. Source that
  has not cleared its bar **holds**: the run parks with the reason
  `source_not_ready`, opens a **source-review task** in the team's queue (see
  [Review](/server/review)), and reports how many blocks are blocked on source.
  Set `source_gate: none` to translate without a source-readiness gate.
- **Translate source that meets the gate.** Settled source is processed per locale,
  memory first: recycle what the shared memory already has, AI-translate the
  remainder, check what was produced. Protected terms stay protected through the
  model.
- **Hold at the target ship-gate.** A locale that clears its `ship_gate` is
  shippable; whatever a machine cannot decide **parks** for review rather than
  shipping under-reviewed.

Editing a source unit re-opens the source gate for changed segments. The next
run checks and regenerates those segments. The model itself, the ladders and gate
thresholds, is documented once on the kapi site:
<KapiLink to="/kapi/convergence#source-first">Source first</KapiLink>.

## Who starts a run

A connector, push policy or explicit command can start a server run:

<LanesDiagram
  lanes={[
    {

      sub: "CMS · design · repository",
      role: "io",
      steps: ["fetch or webhook", "run server-side", "publish / deliver a PR"],
    },
    {
      title: "A push policy",
      sub: "bowrain.converge: on-push",
      role: "qa",
      steps: ["a push arrives", "the server catches up", "results wait for pull"],
    },
    {
      title: "A developer",
      sub: "kapi up",
      role: "translate",
      steps: ["push the drift", "server runs", "progress streams back"],
    },
  ]}
  caption="The same server-side run, started by a connector, a push policy, or a developer's command."
/>

- **From a connector, with no checkout.** Content connected server-side (a
  content platform, a design tool) catches up where it lives when a
  [server-side flow](/server/flows) or automation rule runs over it, and
  publishes back to where it came from. A
  [repository connector](/server/connectors/github) turns a push webhook into a
  run and delivers the results as a pull request, with no pipeline in the
  repository at all.
- **From a push policy.** With `bowrain.converge: on-push` on the recipe's
  `bowrain:` block, every push triggers a server-side run: the project stays
  continuously current without anyone running a command. The policy is explicit
  and per-project, the way `git push` triggering CI is a repository policy. See
  [Automation](/server/automation).
- **From a developer's terminal or CI.** [`kapi up`](/cli/commands/up) on a
  connected project prints its resolved venue first (*server*), pushes the
  drift, streams the run's progress live into the same terminal view, and pulls
  the results down. `kapi up --local` overrides the venue for one run: the work
  executes on that machine and those keys, and the results are pushed so the
  server is never left stale. `kapi up --server` requires the server venue,
  failing rather than falling back (for CI that must never spend local keys).
  See the [kapi connector](/server/connectors/kapi) and
  [the loop in CI](/cli/ci/overview).

## Seeing it

Every surface reads the same derived state:

- **In the web and desktop app**, a project's **Runs** view lists the
  server-side runs (*Running*, *Up to date*, *Parked*) with the trigger
  (*Manual*, *kapi up*, *On push*), the pass count, and a per-language summary
  such as "3 shippable · 1 parked". A **Run now** button starts a run from the
  app, and an in-flight run can be canceled.
- **In the terminal**, [`kapi status`](/cli/commands/status) shows the
  per-language coverage grid, the server standing, and the effective venue and
  `bowrain.converge` policy.
- **In the review session**, parked units are the worklist: a run reports them
  as awaiting a person and still exits zero. Parked work is pending review, not
  an error.

A run started from the app and a run started from a terminal emit the same event
stream. The Runs view, CLI and `--json` output report progress from those events.
