# The context graph

A legal notice, a help article and a release note can describe the same product
with different vocabulary and levels of detail. The appropriate wording depends
on the audience, the surface and the date.

A **content context** records those conditions as coordinates and associates them
with writing guidance. People, checks and AI assistants can retrieve the guidance
that applies to the content they are working on.

## One decision, five rules

A feature rename illustrates why a rule needs a scope:

| Where the words sit | What the rule is |
|---|---|
| Help articles | Use the new name |
| The API parameter | Must not change |
| The changelog | Keeps the old name, because that is what shipped |
| The migration guide | Needs both, side by side |
| Support replies | Recognise the old name for a year, never use it |

The rename requires different rules for different surfaces. A project-wide list
of banned and preferred terms cannot express all of them. The graph associates
each rule with the scope where it applies.

## Profiles and coordinates

A context is a set of **coordinates**:

| Coordinate | The question it answers |
|---|---|
| Audience | **Who** is it for |
| Surface | **Where** does it appear |
| Register | In **what register** |
| Market | For **which market** |
| Validity | **From when until when** |

A **profile** groups coordinates under a name such as *developer reference*,
*end-user help*, *regulated disclosure* or *launch campaign*. Rules use these
coordinates to determine where they apply.

The same scope resolution supports guidance lookups, content checks and reuse of
approved wording.

### The axes a recipe declares

In a project the five questions are answered by named **axes**. Two are
structural and come from the recipe's shape: `product` is the profile a
collection belongs to and `channel` is the surface it ships on, both derived
from a collection's `channel:` key. The rest are declared: `brand` (a workspace
has brands, a brand has products, a product ships channels) and `mode` (what
kind of document sits at a point, in the Diátaxis sense: tutorial, how-to,
reference, explanation) are the named ones, and a project adds any other axis
its content varies along under `defaults.coordinates`. A language is an axis
too. Validity sits on the rule rather than on the point: a rule can start and
stop on a date. See the [project model](/cli/project-model) for the recipe keys.

## Declared where cheapest, inherited from there

Declare shared coordinates at project level. Collections inherit them and can
override individual axes.

For example, a help-centre collection and an API-reference collection can inherit
the same brand coordinate while declaring different channels. Files and passages
cannot declare coordinates individually. To apply different guidance to a file,
place it in a separate collection.

## Rules inherit and expire

Rules apply within their declared scope and may include start and end dates.
More specific rules can override inherited guidance.

For example, support replies may recognise a retired name during a transition
period. A validity window limits that exception without requiring a later edit
to remove it.

## Starting from nothing

A **context scan** reads existing content, such as a repository, published site
or style guide, and proposes axes, a voice profile and terms for review. You can
edit the proposals before accepting them.

See [Context scan](/server/context-scan) for scan inputs and outputs, and
[Voice and corrections](/server/context-voice) for maintaining guidance through
reviewed corrections.

## Agreed rather than assumed

Governed changes require a **change-set**, a named draft of proposed edits. You
can preview its effect on stored content and pilot it on selected content streams
before merging it. Ordinary edits, such as definition changes, apply directly.

Corrections provide evidence for new rules. A reviewer decides which candidates
to promote. See [the Context hub](/server/context) for the approval process and
[Voice and corrections](/server/context-voice) for candidate rules.

## One graph, two scopes

**kapi resolves context for local projects.** **Bowrain shares context across a
workspace** and adds collaborative review, access controls and cross-project
analysis. Both use the same content engine. See
[kapi and Bowrain](/getting-started/kapi-vs-bowrain).

## Where a language fits

Language is another coordinate used to select applicable terms and guidance.
The same model supports source-language checks and translation.
