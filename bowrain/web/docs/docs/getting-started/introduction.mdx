# Bowrain

Bowrain is **the context graph your people and agents plug into** — the
coordinates that fix voice and tone for a specific time, place and audience,
recorded in a form a machine can read. Profiles, vocabulary and content memory
are held on a server and shared across every project, person, and agent — with
collaborative editing, review, automation, and version history around them.

New to the idea? Start with **[The context graph](/getting-started/the-context-graph)**
— what a profile is, what coordinates are, and why a rename is one decision and
five different rules.

Content reaches a workspace from the systems it already lives in. A content
platform, a design file, a code repository, and a developer's checkout are peer
routes in, and everything is ordinary project content once it arrives: same
governance, same review queue, same history.

A team shares one workspace through a browser and a native desktop app —
editing, terminology, content memory, presence, and reviews all live on the
server.

## What Bowrain adds

### Shared, versioned governance

Profiles, vocabulary, and content memory held on the server and shared across
everyone — writers, reviewers, and AI tools — instead of living in each person's
checkout. Changes are versioned and auditable: who approved a term, when a
profile changed, what a piece of text used to say. And the context _learns_:
repeated corrections become versioned, enforced rules, so what a team discovers
by correcting real output is captured instead of lost — see
[Brand voice & corrections](/server/brand-voice).

### Collaboration

A web editor and a desktop app connect to the same server. People work in Visual
and Table views with content memory and terminology in context; edits, presence,
and live updates propagate to every client without a refresh — see
[Real-time collaboration](/server/collaboration).

### Connectors

A workspace syncs against the systems content already lives in — a content
platform (WordPress, HubSpot), a design tool (Figma), a code repository (GitHub,
GitLab), or a developer's checkout (kapi). Most run **server-side, with no local
checkout**: source flows into the governed workspace, gets drafted and checked,
and publishes back to where it came from. See [Connectors](/server/connectors).

### AI that stays on-brand

The workspace's governed vocabulary, content memory, and brand-voice checks are
the context an AI assistant reads — over [MCP](/server/brand-voice) — so
generated and adapted copy is on-voice from the first draft, and corrections
flow back into the shared, enforced checks.

### Automation

Server-side rules run flows when content arrives, a quality gate passes, or a
connector syncs — shared, event-driven workflows for the whole workspace. See
[Automation](/server/automation).

### Stewardship over time

A persistent, versioned content store keeps the history of every block, branch,
and language, so the work compounds: vocabulary decisions, brand-voice
corrections, and remembered text stay with the project as people and tools come
and go.

## Parts of the platform

- **Server** — workspaces, authentication, the versioned content store,
  automation, and the connectors.
- **Connectors** — content platforms, design tools, code repositories, and a
  developer's checkout. Most run server-side with no checkout involved; see
  [Connectors](/server/connectors).
- **Web editor** — a browser-based workbench with Visual and Table views,
  content memory, and terminology.
- **Desktop app** — a native cross-platform editor with offline support.

## Just need local tools?

Bowrain is built on [kapi](https://neokapi.github.io/), an
Apache-2.0 toolchain that runs on its own — extraction, brand and terminology
checks, drafting, pseudo-translation, QA — directly on files, with no server or
account. Reach for Bowrain when the work should persist beyond a single run:
several projects, several surfaces, a memory that compounds, hosted review, or a
team working together.
