# Create content with kapi as the checker

**Goal:** when you are **authoring** new content (there is no frozen source to edit; you are writing the document), use kapi as the checker. You write; kapi parses what you wrote, holds it to the voice profile and terminology, and tells you what to fix. No AI provider is involved. This is the **author → parse → check** loop, the create-side counterpart of [Edit content](/kapi/recipes/rewrite-content), where the source is fixed and you edit existing blocks.

<TabItem value="desktop" label="Desktop" default>

Write in your own editor; the desktop is the checker beside it.

1. **Track the draft.** Add the file to a project collection (or push it through a **quick tool** for a one-off); the collection card shows the format kapi detected for it.
2. **Parse it as the first check.** Open it: **Preview** renders the document as the engine reads it; **Blocks** lists what you actually wrote, block by block. A missing or merged block means the source needs fixing.
3. **Gate on voice and terminology.** The **Checks** view runs the project's bound rules; each finding names its rule and block, with the suggested wording.
4. **Revise and re-run** until the findings clear. A clean check is the finish line.

</TabItem>
<TabItem value="agent" label="Agent (Claude)">

With [kapi connected](/kapi/get-started/use-with-claude), the assistant is the author and kapi stays the checker:

> Draft a release-notes page for the export feature, on brand, using our approved terms.

It loads the voice and wording first (`kapi voice guide`, `kapi terms lookup`) so the first draft is already close, then loops `check_file` → revise until the gate is green. When a check flags a new term, it proposes the [close-the-loop change-set](#close-the-loop-fix-the-content-and-the-rule-together): the content fix and the term rule in one `apply`.

</TabItem>
<TabItem value="cli" label="CLI">

Author in a **generative** format, one kapi can produce from content alone (Markdown, HTML, JSON, YAML, …):

```bash
kapi formats --json | jq -r '.formats[] | select(.generative) | .name'
```

Binary office formats (`.docx`, `.pptx`, `.xlsx`) are editable but not generative: start from an existing file and [edit it in place](/kapi/recipes/rewrite-content) instead. Parse the draft back as the first verification that it is well-formed and says what you intend, then gate it:

```bash
kapi stats draft.md --json                            # size and structure survey
kapi inspect draft.md --jsonl                         # block by block, as a reader sees it
kapi check draft.md --profile-file voice.yaml         # one-off; exit 0 pass, 3 gate failed
kapi check --ship                                     # in a project: every bound gate
```

Load the voice and approved wording **before** writing so the first draft is already close:

```bash
kapi voice guide                          # the voice to follow (no flag inside a project)
kapi terms lookup "dashboard" -t en    # the approved term
```

Fix what the check flags (edit the source directly, or route the fix through `kapi apply` when you want the round-trip and its guards; see [Edit content](/kapi/recipes/rewrite-content)) and re-check until green.

## Close the loop: fix the content and the rule together

When a check flags a term, the durable fix is two changes: correct **this draft** and record the rule so **future** drafts are checked against it. Both are operations in one `kapi apply` change set (requires a [kapi project](/kapi/get-started/first-project)), with the block's `ref` and `rev` from `kapi inspect draft.md --jsonl`:

```json
{"ops": [
  {"op": "replace_text", "at": {"doc": "draft.md", "block": "setup/p#2"}, "if_match": "r:a1b2c3d4e5f60718",
   "edits": [{"find": "control panel", "text": "dashboard"}]},
  {"op": "term", "action": "upsert", "term": "dashboard", "locale": "en", "status": "preferred", "replaces": "control panel"}
]}
```

```bash
kapi apply change.json
```

The **content** operation rewrites the block through the faithful round-trip, refused if the block changed since you read it; the **term** operation, applied after it, is written into the [project store](/kapi/project-store)'s terms tables and recorded as a decision, so `kapi context log` names the new term and the next `kapi check` enforces it. The change set lands whole or not at all: when an operation is refused, nothing is written, and `kapi apply` names the refusal and exits non-zero. Resending a change set that landed is safe, because an operation already in place reports `unchanged`. `apply` also accepts `memory` and `recipe` operations; see [Keep source on brand](/kapi/recipes/keep-source-on-brand) for a `term` operation that adds a word rule.

Writing a rule directly is your decision, so an assistant's `term`, `memory` and `recipe` operations are refused, and the change set that holds them, whether it runs `kapi apply` from its shell or sends the change set through MCP. The assistant applies the content operation on its own and records the rule as a suggestion with `kapi context correct --suggest`, which you keep with `kapi context keep` ([Growing context](/kapi/context-decisions)).
