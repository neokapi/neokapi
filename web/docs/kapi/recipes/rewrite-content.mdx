# Edit content in any format, faithfully

:::note Runs anywhere
No project, provider, or credential needed — you supply the edits, kapi applies them ad-hoc to any source file.
:::

**Goal:** edit the text inside a file without touching its structure — a Word
document, a JSON catalog, a Markdown guide, an HTML page, or any other format
kapi reads. The result is the same file — same keys, same styles, same inline
codes — with only the prose changed. You do the rewriting (simplify docs, fix
off-brand copy, standardize terminology, fit a length budget); kapi parses the
format, enforces a faithful round-trip, and writes the result back. kapi does
not send content to a model to rewrite it.

## Read the blocks

Size the job first with `kapi stats` (block, word, and character totals — see
[Feed content to your AI](/kapi/recipes/ingest-for-ai) for the survey step),
then read the blocks. `kapi inspect` returns one record per content block — the
`text`, the block's structural role and nesting level, a stable `id`, and a
`content_hash`:

```bash
kapi inspect guide.md --jsonl        # one JSON object per line, for streaming
kapi inspect guide.md -f markdown    # override format detection
```

Two fields anchor an edit:

- **`text`** renders inline codes (links, bold spans, placeholders) as
  `<x id="…"/>` tokens. **Keep every token in your edited text** — they are the
  markup the round-trip reconstructs. A placeholder is `<x id="1/"/>`; a paired
  span opens with `<x id="1"/>` and closes with `<x id="/1"/>`.
- **`content_hash`** is the block's canonical identity (a hash of its plain
  source text, not of the placeholder `text`). Send it back with the edit so kapi
  can tell the block is still the one you read.

`kapi inspect` does not modify the file.

## Edit, then apply

Rewrite the blocks you want to change, and produce one `content` entry per
changed block — JSONL, one per line — naming the block's `file`, `id`, the
`content_hash` you saw, and your new `text`:

```json
{"kind":"content","file":"guide.md","id":"p3","content_hash":"a1b2c3…","text":"See the <x id=\"1/\"/> dashboard."}
```

`kapi apply` is the one write verb. It reads the change-set from a file, an
argument, or stdin, and writes each named file in place — no model called:

```bash
kapi inspect guide.md --jsonl > blocks.jsonl
# Now rewrite the "text" of each block you want to change — keeping every
# <x id="…"/> placeholder — and save the changed ones as content entries to
# edits.jsonl. (This is the step you, or your AI assistant, do; there is no
# command for it — that is the point: kapi never sends the text to a model.)
kapi apply edits.jsonl --diff           # preview the content changes, write nothing
kapi apply edits.jsonl                    # apply in place
kapi apply edits.jsonl --in-place=.bak    # apply, keeping a .bak
```

`--diff` runs the edit and prints a unified diff instead of writing — only the
text that changed appears; headings, list markers, code fences, and inline codes
stay untouched.

## The two guards

`apply` writes a block only when both guards pass; a blocked edit leaves that
block untouched and is reported, so nothing is silently corrupted:

- **Drift guard.** A block whose current `content_hash` no longer matches your
  entry changed since you inspected it — the edit is marked **stale** and skipped.
- **Inline-code guard.** An edited `text` that drops, invents, duplicates, or
  unbalances an `<x id="…"/>` token is **rejected** rather than written back
  with broken markup.

Either outcome exits on the **gate code (3)**, distinct from an operational
error — a signal to re-inspect the affected blocks and retry with fresh hashes.
`apply` is idempotent: re-running a partly applied change-set is safe. The same
change-set can also carry asset edits (a glossary term, a brand rule — see
[Create content](/kapi/recipes/create-content)) or a `kind:"review"` decision
that approves a translated unit
([Convergence](/kapi/convergence#review-a-decision-in-the-project-state-store)) —
one write verb, different `kind`s.

## What "faithfully" means

Only the extracted prose changes; everything outside it — `.docx` character
styles and table borders, JSON keys and non-string values, Markdown headings and
fences — is reproduced byte for byte. This is what makes editing **binary**
office formats (`.docx`, `.pptx`) safe; `kapi formats list` marks such formats
`faithful` in its Edit column.

## Verify the result

After editing, run `kapi check` to confirm the result meets your content rules —
deterministic, read-only, exit `0` on pass and `3` on gate failure (`--json` for
the structured report):

```bash
kapi check guide.md --max-chars 500 --forbid "utilize"   # ad-hoc rules
kapi check guide.md --profile company-voice              # a named checkset
```

Read the findings, fix the flagged blocks through another `apply` pass, and
re-run until the gate is green. (See [Checks](/framework/checks) for the
`kapi.check/v1` report model.)

## In an AI assistant's fix-loop

When kapi is wired as an [MCP server](/reference/mcp) (`kapi mcp`), an assistant
drives this same loop through structured tool calls — `extract_content` to read
blocks, `check_file` for findings, `apply_edits` to write the change-set back,
`check_file` again to confirm the gate. No model is called for the rewrite: the
assistant is the writer, kapi enforces the round-trip and drift-checks each edit
by `content_hash`. See [Use with Claude](/kapi/get-started/use-with-claude) for
the skill and MCP setup.

## In a project

In a `.kapi` project, `kapi inspect` and `kapi check` run against the recipe's
declared content with no file argument, and `kapi apply` lands edits against the
named files. See [Create your first project](/kapi/get-started/first-project).
