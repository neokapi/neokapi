# The kapi loop in CI

Source content changes on every merge, and everything derived from it (its
translations, its voice and terminology conformance) falls behind. That drift
is the normal state of a shipping project. Running
[the kapi loop](/kapi/convergence) in CI keeps every language caught up from
the pipeline that produces the drift: close what a machine can close, deliver
it as a reviewable pull request, and enforce the release bar on merges, with
content quality treated like any other test. This covers the source language
too: the ship gate includes the source gates (voice, terminology) alongside
translation coverage and the rule-based checks.

Inside a pass, for every language behind its gate, the default flow does three
things in order: **reuse**, where exact content-memory matches fill first, for
free, and an edited source carries its previously approved translation into the
prompt as reference; **translate**, where the configured AI provider fills what
remains, with the project's terminology and voice context; **check**, where
deterministic checks run over what was produced (placeholder integrity, inline
tags, do-not-translate terms). A block with a failing finding still counts as
*translated*, and the finding holds its locale out of shipping until it is
fixed, so bad output can never lift a language over its gate. What a machine cannot
decide **parks** for [review](/kapi/recipes/review-and-approve); an approval is
recorded in the project store, and the next run sees it.

Three commands carry the whole model, and they divide the work cleanly:

| Command | Role | Exit behavior |
|---|---|---|
| `kapi status` | **Observe**: per-locale coverage and gate standing | Always `0`: behind is pending work |
| `kapi up` | **Produce**: runs the kapi loop | `0` whether the run caught everything up or parked work for review; non-zero only when the run broke |
| `kapi check --ship` | **Enforce**: the release bar | `0` pass, `3` gate unmet, `4` the check did not run, `1` operational error |

An ordinary build never fails because a target language is behind. The gate is
the explicit, opt-in enforcement point: wire it into merge-request pipelines
and a quality regression cannot merge, while day-to-day drift flows through
review instead of breaking builds.

## Source first: settle before you fan out

The loop is [source-first](/kapi/convergence#source-first): it settles the source
and holds each block's source until it reaches `translate_after` before translating any language, because a term left
unresolved or a sentence left off-brand in the source is paid for once per
language and again on the fix. In CI this shows up two ways. `kapi check --ship`
runs the project's `source_gate` alongside the target ship gates, so a merge whose
**source** is off-brand or below its terminology bar fails the gate the same way a
target-coverage regression does. And under source-first convergence, source below the project's
`defaults.translate_after` level **holds** (reported as `source_not_ready`,
routed to a source review) rather than spending on a machine translation of
content that is about to change. See [Source first](/kapi/convergence#source-first)
for the model.

| CI | Install | Run |

| GitLab CI | none needed (the components run on the image) | [`kapi-components`](https://gitlab.com/neokapi/kapi-components) from the CI/CD Catalog |

## Catch up on a schedule, deliver a pull request

The produced translations land as a branch and a pull request carrying the
run report: outcome, passes, parked locales. A run that **parks** (work
remains that needs a person) still delivers what it did catch up; the parked
locales are the review queue.

<Tabs groupId="ci" queryString>
<TabItem value="github" label="GitHub Actions" default>

```yaml title=".github/workflows/translations.yml"
name: Translations
on:
  schedule:
    - cron: "0 6 * * 1-5"
  workflow_dispatch:

jobs:
  up:
    uses: neokapi/kapi-workflows/.github/workflows/up.yml@v1
    permissions:
      contents: write
      pull-requests: write
    secrets:
      anthropic-api-key: ${{ secrets.ANTHROPIC_API_KEY }}
```

The reusable workflow composes `setup-kapi`, `kapi-action`, and a delivery
step that opens the pull request. Used directly, the action only reports:
`has-changes` and `changed-files` feed a delivery step you own (plain git,
`git-auto-commit-action`, `create-pull-request`), so the token, the authorship
and the review policy are stated in your workflow. One GitHub behavior to
know: pushes made with the workflow's own `GITHUB_TOKEN` trigger no
workflows, so give the delivery step a fine-grained PAT or a GitHub App token
when CI or deploys should react to delivered translations.

</TabItem>
<TabItem value="gitlab" label="GitLab CI">

```yaml title=".gitlab-ci.yml"
stages: [build, test, kapi, deploy]

include:
  - component: gitlab.com/neokapi/kapi-components/up@0.2.0
    inputs:
      stage: kapi
      deliver: mr
```

The component's job runs on scheduled and web-triggered pipelines and on
pushes to the default branch by default. Without a `deliver` input it only
reports what changed, for a delivery job of your own; `deliver: mr` opens the
merge request through the API (`GITLAB_API_TOKEN`, api scope). The job exposes
`KAPI_OUTCOME`, `KAPI_PASSES`, `KAPI_PARKED_LOCALES` and `KAPI_HAS_CHANGES` to
downstream jobs via dotenv, and lists the changed paths in the
`kapi-changed-files.txt` artifact.

The pipeline's `stages:` list must declare the stage the `stage` input names,
or GitLab refuses to create the pipeline. The job writes its report files
(`kapi.env`, `kapi-up.ndjson` and `kapi-changed-files.txt`) into the checkout,
so list them in `.gitignore`; otherwise the job counts them as changes and a
delivery commits them.

</TabItem>
</Tabs>

## Gate merges on content quality

`kapi check --ship` runs the project's bound quality gates (voice, terminology,
rule-based checks, staleness) plus its ship/source coverage gates, and exits `3`
when any gate is unmet. Machine-produced translations fail quietly: a dropped
placeholder, a competitor's term, wording that drifts off the approved
vocabulary. The gate makes the pipeline find them before a reader does.

<Tabs groupId="ci" queryString>
<TabItem value="github" label="GitHub Actions" default>

```yaml title=".github/workflows/ship-gate.yml"
name: Ship gate
on:
  pull_request:
    paths: ["content/**", "src/locales/**"]

jobs:
  ship-gate:
    uses: neokapi/kapi-workflows/.github/workflows/gate.yml@v1
    permissions:
      contents: read
      pull-requests: write
```

An unmet gate fails the job with a distinct "gate unmet" annotation and posts
one sticky report comment that re-runs update in place. A gate that did not run
(exit `4`) fails the job with a "did not run" annotation that names the cause.

</TabItem>
<TabItem value="gitlab" label="GitLab CI">

```yaml title=".gitlab-ci.yml"
include:
  - component: gitlab.com/neokapi/kapi-components/check@0.2.0
```

The job runs on merge-request pipelines and on pushes to the default branch,
fails on exit `3`, and posts one threaded MR note with the failing gates and
findings; the full `--json` report is kept as a job artifact. Exit `4`, a gate
that did not run, fails the job too, and the report names the cause. To leave
pushes to the default branch ungated, set the `rules` input to merge-request
pipelines alone.

</TabItem>
</Tabs>

The [Ship gates & CI](/kapi/recipes/ship-gates-and-ci) recipe walks the
gate end to end, including the import step that lets an `established`
threshold pass on a runner.

## Settle suggestions after a merge {#settle-suggestions-after-a-merge}

A suggestion becomes a rule once a person's work backs it, and a change
merged to the default branch is such a signal: a person reviewed and merged it
([how a suggestion becomes a rule](/kapi/context-decisions#how-a-suggestion-becomes-a-rule)).
`kapi context sync --merged <range>` reads the change a range of commits made,
counts it as evidence for every suggestion whose preferred wording it added or
whose avoided wording it removed, and makes each suggestion the evidence backs
a rule when nothing contradicts it. A change counts only in the files where the
suggestion holds, so a merge never applies a rule more widely than where it was
seen. It names the pull request and the merger,
read from the last commit when you pass neither `--pr` nor `--merger`. The same
range records the same evidence, so a rerun changes nothing.

The same command syncs the context, so the rules the merge settled reach the
rest of the team at once. A project that shares its context nowhere settles
the merge on the machine that runs it. On a developer machine, run it after
pulling the default branch:

```bash
git pull
kapi context sync --merged ORIG_HEAD..HEAD
```

On a runner, run it after a push to the default branch. With a `git` backend
the job needs the full history and permission to push the context ref:

```yaml title=".github/workflows/settle.yml"
name: Settle context
on:
  push:
    branches: [main]

permissions:
  contents: write          # push the context ref

jobs:
  settle:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - uses: neokapi/setup-kapi@v1
      - run: >-
          kapi context sync
          --merged "${{ github.event.before }}..${{ github.sha }}"
          --merger "${{ github.actor }}"
```

A project with no backend keeps what the merge settled in the runner's
workspace, so keep the kapi data directory between runs (`KAPI_DATA_DIR` and a
cache step) or the evidence is lost with the runner.

## Report the cost of a change on its pull request

`kapi up --plan` dry-runs the loop: pending blocks, content-memory leverage, and a
token estimate, with no writes, no provider calls, no keys. Posted on the pull request
that created the work, it answers "what does this change cost in translation?"
before anyone merges:

<Tabs groupId="ci" queryString>
<TabItem value="github" label="GitHub Actions" default>

```yaml
- uses: neokapi/kapi-action@v1
  with:
    plan: "true"
    pr-comment: "true"
```

</TabItem>
<TabItem value="gitlab" label="GitLab CI">

```yaml
include:
  - component: gitlab.com/neokapi/kapi-components/up@0.2.0
    inputs:
      stage: kapi
      plan: true
      rules:
        - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

As in the catch-up job, the pipeline's `stages:` list must declare the `kapi`
stage.

</TabItem>
</Tabs>

> This change leaves **42 block(s)** of pending translation work: 30
> recoverable from content memory, 12 for AI (~450 tokens estimated).

## Credentials and state on a runner

- **A producing job uses an API key**: set a provider key (for example
  `ANTHROPIC_API_KEY`) as a CI secret. A subscription sign-in is bound to your
  user and its usage window; see
  [Let kapi run Claude](/kapi/get-started/use-with-claude#let-kapi-run-claude).
  In a server-connected project (a recipe that declares a server venue) the server
  holds the keys instead, and the job authenticates with a server token.
- **A gate-only job needs no keys at all**: `check --ship` and `up --plan`
  read the working tree.
- **A runner starts with an empty context store**, because a project's terms,
  voice profiles, content memory and approvals live in a workspace on the
  machine that holds them. Sync the project's context before the job and again
  after it; see [below](#pull-context-before-push-after).
  A job never commits `.kapi/work/store.db`.
- **The parse cache is the part to carry between runs**: `.kapi/work/cache/docs`
  is gitignored, rebuilt on a fresh runner, and keyed by each file's path and
  content, the parse configuration, the recipe and the kapi build, so a restored
  entry changes no result. `setup-kapi` carries it by default, and a job that
  uses the action needs no cache step of its own:

  ```yaml
  - uses: neokapi/setup-kapi@v1
    with:
      version: "1.2.0"
      # cache-tm: false turns the parse cache off
  ```

  Without the action, cache that one directory:

  ```yaml
  - uses: actions/cache@v6
    with:
      path: .kapi/work/cache/docs
      key: kapi-parse-${{ runner.os }}-${{ hashFiles('kapi.yaml', 'src/locales/en/**') }}
      restore-keys: kapi-parse-${{ runner.os }}-
  ```

  **Cache nothing else under `.kapi/work`.** `store.db` is this checkout's
  projection of its working tree, and a restored copy changes what a run
  reports: on a fixture project it turned a failing `check --ship` into a
  passing one and a locale's coverage from 0% to 100%. The other entries under
  `cache/`, such as the extraction batches, the redaction record and the sync
  state, belong to the checkout that wrote them. Server-connected projects skip
  the cache entirely; the project's context lives on the server.

:::note[Works with Bowrain]
Everything on this page runs the loop inside your own CI. A project whose recipe declares a `bowrain:` block runs the same loop on a Bowrain server instead: `kapi up` pushes, the server catches every locale up against the workspace's shared memory and terminology, and the run streams back, with review handled in the Bowrain web app rather than in your checkout. See the [Bowrain documentation](https://bowrain.cloud/docs/).
:::

## Sync context around a job {#pull-context-before-push-after}

A project that declares a [context backend](/kapi/context-portability#sharing-context-through-a-backend)
brings its context to a runner with `kapi context sync --no-push` before the
job, which reads the shared context and shares nothing, and shares what the job
recorded with `kapi context sync` after it. With the `git`
backend the context is kept on a ref of the repository itself, so the job
needs nothing but the checkout and permission to push:

```yaml
permissions:
  contents: write          # push the context ref
steps:
  - uses: actions/checkout@v5
  - uses: neokapi/setup-kapi@v1
  - run: kapi context sync --no-push
  - run: kapi up
  - run: kapi context sync
  - run: kapi check --ship
```

A runner that skips the sync holds the translations the checkout carries and
no record of the source each was made from, so a source edited since a
translation was made is not graded stale there. `kapi up` and `kapi status`
say so in one line naming `kapi context sync`.

`kapi context sync` fetches the context ref itself (`refs/kapi/context`),
which a checkout does not. A pull request from a fork can read the shared
context and cannot share back to it, so its jobs run `kapi context sync
--no-push` and leave sharing to a job that runs in the repository. A sync that
cannot reach the backend exits with status 5 and changes nothing, so a job can
retry it.

A job whose gates depend on terms or a voice the repository carries runs
`kapi store import` before the gate, which reads them into the project's store.
