# Growing context

A new project starts with no terms, voice profile or approved wording. Its
context grows as you work: an assistant notices the name the files always use,
or the word you changed in its draft, and records it. Each note arrives as a
**suggestion**. A suggestion advises from the moment it is recorded, and you
decide about it when it suits you. A suggestion you keep becomes a **rule**.

| Command | Does |
| --- | --- |
| `kapi context review` | decide about what is waiting: keep, drop, choose a side, apply more widely |
| `kapi context reset --before <when>` | go back to how the context stood at an earlier point |
| `kapi context note` | record what you noticed, or what a person changed (an assistant runs this) |
| `kapi context log` | list what was recorded, or what one assistant session recorded |

## An assistant notes as it works

A coding agent using kapi's [MCP server](/reference/mcp) records with the
`context_note` tool; one running kapi from its shell runs `kapi context note`.
Each call records one thing:

```bash
# something the files do every time
kapi context note --term Quickcast --instead-of "Quick cast" \
  --seen-in docs/guide.md --quote "Quickcast forecasts the next hour."

# wording a person changed, and the rule it implies
kapi context note --from "sign in" --to "log in" --seen-in web/src/auth.tsx --suggest

# a fact in prose
kapi context note "the docs address the reader as you"
```

From `--term` and `--instead-of`, kapi works out the other spellings to avoid,
with spaces, hyphens and capitals. This note avoids `Quick cast`, `Quick-cast`,
`QuickCast` and `quickcast`.

Everything one assistant run records belongs to its **session**. The assistant
ends its report with the session's id and the command that reviews it:

```bash
kapi context log --session this           # the assistant reads back its own run
kapi context review --session s4980103f5148
```

An assistant can take back a note of its own that was wrong, in the session
that recorded it:

```bash
kapi context note --withdraw 0n794e2gk7 --why "recorded the wrong way round"
```

## A suggestion never stops your work

A suggestion advises at once: `kapi context <path>` lists it under
*Suggested, not yet established*, and checks report text that goes against it.
No check fails on it and no score changes until it becomes a rule. A
suggestion nobody answers keeps advising, so nothing here has to be cleared.

## Reviewing what kapi learned {#reviewing-what-kapi-learned}

```bash
kapi context review
```

In a terminal, review asks about each suggestion in turn and shows the
evidence behind it:

```
[1/2] 0pjby7f9fx  Write Quickcast, not Quick cast, Quick-cast, QuickCast or quickcast.
  seen "Quickcast forecasts the next hour." in docs/billing.md
  noticed by claude-code
k keep, w keep and apply more widely, d drop, s skip, q quit:
```

Each answer is recorded as you give it, so quitting part way keeps what you
decided.

Run anywhere else, such as in a script or by an assistant, review lists what
is waiting since you last looked, with the id each decision takes:

```
Since you last looked (Tuesday 22 September 09:14):

Needs you
  These rules say different things about the same word. Choose one, and the others are set aside.
    0njy7pxnst  Write log in, not login.
          noticed by codex
    0njy7pwmtj  Write sign in, not login.
          noticed by claude

Established
  0njy7pghcn  Write studio, not business.
        seen "Our business plan" in docs/billing.md
        docs/ says "studio" 41 times and "business" twice
        merged in #412 · your correction in docs/billing.md

Suggested
  Names and spellings
    0njy7pfhjp  Write Quickcast, not Quick cast, Quick-cast, QuickCast or quickcast.
          seen "Try Quick cast today" in docs/intro.md
          seen in 2 sessions · noticed by claude

kapi knows 23 rules for Fernwell; 4 are new this week. 1 suggestion is advising.
```

The sections come in the order you read them: disagreements that need you,
the rules that came into force and what they rest on, suggestions grouped by
theme (names and spellings, words to avoid, how the project writes), content
drifting away from a rule, and the project in numbers.

Reviewing moves your "since you last looked" marker, which kapi keeps on this
machine and never in the project. `--peek` leaves it where it is, `--since`
reads from a date instead, and an assistant reading the list never moves it.
`--json` prints the same sections for a program. Kapi Desktop shows the same
list when you open a project's Context.

## Keeping a rule {#keeping-is-what-makes-a-rule-bind}

Name a suggestion by its id. Any start of an id that names one suggestion will
do, and `--keep` repeats:

```bash
kapi context review --keep 0pjby7nz7z
```

```
#0pjc4e498b  2026-10-08T13:03:48Z  person  keep  of #0pjby7nz7z
  written to the project's terms store
```

A rule you keep is in force from then on, in every command that reads the
project's context, on any branch and in any worktree. A use of the word it
avoids fails a check, unless the rule is advisory, in which case it reports.

Change the rule as you keep it, and say why:

```bash
kapi context review --keep 0pjby7nz7z --use "module" --advisory --note "house style"
```

Keep everything one session suggested that nothing disagrees with:

```bash
kapi context review --session s4980103f5148 --keep all
```

## Dropping a suggestion or a rule

```bash
kapi context review --drop 0pjby7f9fx --note "we say it both ways on purpose"
```

A dropped suggestion stops advising at once. Dropping a rule already in force
takes it back out of the project's terms or content memory, so checks stop
failing on it. The record stays either way, so the same suggestion is
recognisable the next time somebody makes it.

To change your mind about a rule, decide again: drop it, or keep a different
one.

## How a suggestion becomes a rule {#how-a-suggestion-becomes-a-rule}

Keeping is the direct way. A suggestion also becomes a rule when your own work
backs it and nothing contradicts it:

- you change wording toward it, and an assistant records your change
  (`kapi context note --from widget --to component --seen-in docs/guide.md`);
- a change that writes its preferred form, or removes a form it avoids, is
  merged to the default branch (`kapi context sync --merged`, run after a
  merge; see [the kapi loop in CI](/kapi/convergence-in-ci#settle-suggestions-after-a-merge)).

Other evidence adds to a suggestion's standing without making it a rule:
another session recording the same thing, an agent's edit writing the
preferred form, and your content writing it, which `kapi check` over the whole
project and `kapi up` count. The review list shows the standing as plain
counts:

```
0njy7pfhjp  Write Quickcast, not Quick cast, Quick-cast, QuickCast or quickcast.
      seen in 3 sessions · merged in #412
```

Evidence against a suggestion is a change away from it, its withdrawal, or
your content moving to a form it avoids after it was recorded. Any of these
beside evidence from you leaves the suggestion waiting for you to decide. Time
alone makes nothing a rule.

## When two suggestions disagree

Two suggestions that name different forms for one word are **contested**.
Both still advise, review shows them together under *Needs you*, and neither
can be kept on its own. Choose one side:

```bash
kapi context review --choose 0njy7pxnst
```

The side you choose is kept and the other is dropped. `--keep all` for a
session leaves a contested suggestion where it is and says so.

A suggestion that contradicts a rule is contested too, and the rule stays in
force. When you change wording against a rule yourself, the rule is contested:
it reports instead of failing, so your own edit never fails your build. Keep
the rule again, or drop it, to settle it.

## Where a rule holds

A rule holds where its evidence was seen: a term noticed in one product's
reference pages holds for that product, and stays out of another product's
tutorials. The [Context](/kapi/context#the-context-space) page explains how the
recipe divides a project.

Apply a rule more widely as you keep it, or later, by naming a rule already in
force:

```bash
kapi context review --keep 0pjby7nz7z --widen-to project     # across this project
kapi context review --keep 0pjby7nz7z --widen-to workspace   # in every project you work on
kapi context review --keep 0pjby7nz7z --widen-to mode        # across every mode, the rest unchanged
```

A rule applied to the workspace holds in every project on this machine. A
project with its own decision about the word keeps it, because the more
specific answer wins.

## Going back to an earlier state

An assistant run can record a great deal in an evening. Go back to how the
context stood before it:

```bash
kapi context reset --before s4980103f5148 --dry-run
kapi context reset --before s4980103f5148 --note "start over"
```

```
Set aside 2 suggestions and rules and 2 decisions recorded since s4980103f5148.
  #0pjby7f9fx  2026-10-08T13:00:24Z  agent claude-code/s4980103f5148  observe  term "Quickcast", not "Quick cast", "Quick-cast", "QuickCast", "quickcast"  [suggested]
  #0pjby7nz7z  2026-10-08T13:00:25Z  agent claude-code/s4980103f5148  correct  term "log in", not "sign in"  "sign in" became "log in"  [established]
Recorded as reset #0pjc4e94p0; `kapi context reset --before 0pjc4e94p0` takes it back.
```

`--before` takes an assistant session, a date such as `2026-10-01`, an
instant, or an id from `kapi context log`. Everything recorded from that point
on is set aside, including what people decided since, and the project's terms,
approved wording and voice are rebuilt as they stood. Nothing is erased: what
was set aside stays in the history marked `reset`, and the reset is recorded
too, so resetting to before it brings everything back. `--dry-run` says what
would be set aside without doing it.

Reset works on the whole context from a point onward. To change one rule,
decide again in review.

## Who may do what

People and assistants both record notes. Only a person keeps, drops or chooses
a suggestion, changes somebody else's suggestion, applies a rule more widely,
imports into the project's store, or resets. kapi refuses these from an assistant and
tells it to ask you to run `kapi context review`. The evidence of a merge, and
the rules it settles, are recorded as kapi acting for the merge, never as an
assistant.

An assistant can withdraw only its own notes, in the session that recorded
them.

## How kapi knows who recorded a note

The MCP server identifies the caller as an assistant, uses the client's name,
and groups its notes under one session. For shell commands, kapi recognises
supported agent hosts from their environment and assigns an assistant identity
and session automatically. Three variables cover the rest:

| Variable | Says |
| --- | --- |
| `KAPI_ACTOR` | `agent` or `person`, for a shell kapi would otherwise read the other way |
| `KAPI_AGENT_NAME` | what the assistant is called, for a host kapi does not recognise |
| `KAPI_AGENT_SESSION` | the id that groups this run, for the same case |

When the host provides no session id, kapi derives one from the process tree,
so the commands of one run share a session. On Windows, where that information
is unavailable, each command is its own session unless `KAPI_AGENT_SESSION` is
set. When kapi cannot tell, it treats the caller as an assistant, so what it
records stays a suggestion for you to review.

## `kapi apply` writes the same history

The term and content-memory changes of `kapi apply` are decisions about the
same context, and appear in `kapi context log` beside the rest:

```
#0n79x4m0cb  2026-09-21T19:37:31Z  person  edit  term "use", not "leverage"  [established]
  applied with `kapi apply`
```

A person's changes are in force at once. An assistant's term, content-memory
and recipe changes are refused, whether it sends them through the MCP
`apply_edits` tool or runs `kapi apply` from its shell, because writing a rule
directly is a person's decision. The assistant records the rule with
`kapi context note` instead, and you keep it. `kapi store import` also puts
context in force directly, and records each file it read.
