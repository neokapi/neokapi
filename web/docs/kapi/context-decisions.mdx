# Growing context

A new project knows nothing. It has no terms, no voice profile and no approved
wording, and it should not: the words a project cares about are the ones it
turns out to use, and nobody knows those on the first day.

Context grows out of the work instead. Someone notices how the product name is
written. A rule is proposed from a hundred pages that agree. You confirm it, and
from then on checks hold new writing to it. When you correct a translation, that
correction is evidence for the next rule.

Eight verbs are that loop. The first three record; the rest are the decisions.

| Verb | Does |
| --- | --- |
| `kapi context observe` | record a fact about how the project writes, with where you saw it |
| `kapi context propose` | record a rule about a word, with where you saw it |
| `kapi context correct` | record wording somebody changed, and the rule it implies |
| `kapi context log` | show what has been recorded and decided |
| `kapi context confirm` | make a proposed rule binding |
| `kapi context discard` | reject one |
| `kapi context revert` | undo an operation, or everything one agent run did |
| `kapi context widen` | put a confirmed rule in force somewhere broader |

## An agent records as it works

A coding agent with kapi's [MCP server](/reference/mcp) keeps the first three as
habits inside whatever else it is doing: `context_observe` while it reads the
project, `context_propose` where the project is consistent about a word, and
`context_correct` the moment you change its wording. One call, one thing,
without stopping to ask you.

Everything it records is a candidate under a **session** of its own, so you can
read a run's whole contribution in one place, or undo it in one command:

```bash
kapi context log --session s4980103f5148      # what one run recorded
kapi context revert --session s4980103f5148   # undo all of it
```

It ends its report with the same session id. Nothing it recorded is in force
until you confirm it.

## A proposal never stops your work

Propose a rule and say where you saw the word:

```bash
kapi context propose utilise --use use --seen-in docs/guide.md
```

From that moment a check reports the word wherever it appears:

```
  severity  rule              location                         message
  NEUTRAL   voice.vocabulary  docs/guide.md:getting-started/p  Proposed rule about "utilise", not yet confirmed
                                                               ↳ Use "use" instead

PASS configured checks: score 100/100 · 1 finding(s) (0 critical, 0 major, 0 minor)
```

The finding is a note. It carries no penalty, it does not lower a score, and it
cannot fail a check or a gate, not even under `--strict`. That is what makes it
safe to let an agent propose rules while you work: whatever it suggests is
visible and nothing it suggests can break a build.

A rule about a word in the voice profile's vocabulary rather than the project's
terms takes `--list`:

```bash
kapi context propose Ripgrep --use ripgrep --list forbidden --severity major
```

## Confirming is what makes a rule bind

Read what is waiting:

```bash
kapi context log --status candidate
```

```
#5  2026-09-21T19:36:17Z  agent claude-code/s8d7fb12ba4c7  correct  term "widget", use "component"  "widget" became "component"  [candidate]
  seen in docs/guide.md getting-started/p: "We utilise the widget to configure your account."
#2  2026-09-21T19:22:20Z  agent claude-code/s4980103f5148  observe  note "The product is written \"Acme Widget\" in headings and \"the widget\" in running text."  [candidate]
  seen in docs/guide.md: "We utilise the widget to configure your account."
```

Then decide, by the id in the first column:

```bash
kapi context confirm 5
```

```
#7  2026-09-21T19:37:02Z  person  confirm  of #5
  written to terms.json
```

Confirming writes the rule into the file your recipe binds, so `git diff` shows
the decision like any other change, and every command that reads your project's
context sees it from there. From now on the rule bites at the severity it
carries: `minor` and `neutral` report, and anything else fails a check.

Change the rule as you confirm it:

```bash
kapi context confirm 5 --use "module" --severity critical
```

Reject it instead with `kapi context discard 5`. Either way the record stays in
the log, so the same suggestion is recognisable the next time somebody makes it.

## Undoing

An agent run can propose a great deal in an evening. Undo all of it at once:

```bash
kapi context revert --session s4980103f5148
```

Everything that run recorded stops answering, and any rule it got confirmed is
taken back out of your terms, your voice profile or your content memory, and out
of the committed file it was written into. What a check said before that run and
what it says after the revert are the same answer.

Undo one operation with `kapi context revert 5`.

Nothing is erased. Reverted operations stay in the log, marked reverted.

## Where a rule holds

A rule holds where its evidence was seen. A word you decided about in one
product's reference pages says nothing about another product's tutorials, which
is usually what you want: house style is rarely one thing across a whole
company.

When it is one thing, say so:

```bash
kapi context widen 5 --to workspace
```

That rule is then in force in every project you work on here. A project that has
its own decision about the word keeps it, because the more specific answer
always wins.

You can also widen past a single axis of the point the rule sits at, which keeps
it specific about everything else:

```bash
kapi context widen 5 --to mode
```

## Who may do what

Anyone may say what they saw. An agent observes, proposes and records
corrections, and everything it records is advice.

Deciding belongs to a person. Confirming a rule, editing what someone else
proposed, rejecting it, withdrawing a rule already in force and widening one are
all yours. An agent that tries is refused, and told so: its tools carry no verb
for any of them.

An agent may withdraw its own proposal while nobody has decided on it, which is
how a run cleans up after itself.

## How kapi knows who recorded an entry

Over the MCP server the answer comes with the call: that server is serving an
agent, it has the client's name, and it groups its run under one session.

From a shell kapi reads the environment. A coding agent host puts every command
it runs into an environment of its own, and kapi recognises the common ones by
the variable each of them sets, so an agent that reaches these verbs from a
shell records as an agent, under a session, with no flag to pass. Its own run
reads back with:

```bash
kapi context log --session this
```

Three variables cover the rest.

| Variable | Says |
| --- | --- |
| `KAPI_ACTOR` | `agent` or `person`, for a shell kapi would otherwise read the other way |
| `KAPI_AGENT_NAME` | what the agent is called, for a host kapi does not recognise |
| `KAPI_AGENT_SESSION` | the id that groups this run, for the same case |

A host that names no session of its own gets one derived from its process, so
the separate kapi commands of one run share an id and a second run gets
another. Where a machine keeps its process tree out of reach, which is the case
on Windows, the id covers one command, and `KAPI_AGENT_SESSION` is how a host
says otherwise there.

kapi errs toward the agent. Reading a person as an agent costs one
confirmation, which the entry was heading for anyway; reading an agent as a
person would put an unreviewed rule on the record with your standing behind it,
outside `--actor agent` and beyond the reach of `revert --session`.

## `kapi apply` writes the same history

The asset entries of `kapi apply` are decisions about the same context, so they
appear in the same log:

```
#9  2026-09-21T19:37:31Z  person  confirm  of #8
#8  2026-09-21T19:37:31Z  person  propose  term "leverage", use "use"  [confirmed]
  applied with `kapi apply`
```

They are confirmed the moment they land, because you ran the command.
