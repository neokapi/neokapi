# Growing context

A new project starts with no terms, voice profile or approved wording. You can
build its context as you work: record a consistent product name, suggest a
preferred spelling, or capture a correction. Review each suggestion before
establishing it as a rule.

The following commands record observations, show their history and manage the
rules that checks enforce.

| Verb | Does |
| --- | --- |
| `kapi context observe` | record something you noticed, such as the form the project uses for a name, with where you saw it |
| `kapi context correct` | record wording somebody changed, and the rule it implies |
| `kapi context log` | show what has been recorded and decided |
| `kapi context keep` | establish suggestions as rules |
| `kapi context drop` | set a suggestion aside |
| `kapi context withdraw` | take back a suggestion you recorded |
| `kapi context revert` | undo an operation, or everything one agent run did |
| `kapi context widen` | put an established rule in force somewhere broader |
| `kapi context settle` | establish the suggestions your own work backs, such as a merged change |

## An agent records as it works

A coding agent using kapi's [MCP server](/reference/mcp) can record consistent
wording with `context_observe` and your edits with `context_correct`. Each call
records one observation or correction as a suggestion.

Everything it records is a suggestion under a **session** of its own, so you can
read a run's whole contribution in one place, keep it in one command, or undo
it in one command:

```bash
kapi context log --session s4980103f5148      # what one run recorded
kapi context keep --session s4980103f5148     # keep all of it
kapi context revert --session s4980103f5148   # undo all of it
```

It ends its report with the same session id. Nothing it recorded is in force
until something you did backs it: you keep it, correct wording its way, or
merge a change that writes it
([how a suggestion becomes a rule](#how-a-suggestion-becomes-a-rule)).

## A suggestion never stops your work

Name the form the project uses, a form it avoids, and say where you saw it:

```bash
kapi context observe --term Quickcast --instead-of "Quick cast" --seen-in docs/guide.md
```

kapi derives spelling variants, including hyphenation and capitalisation. This
suggestion identifies `Quick cast`, `Quick-cast`, `QuickCast` and `quickcast` as
alternatives to avoid. Checks report these forms, but suggested rules have no
effect on scores or gate results until you keep them.

## Establishing a rule {#keeping-is-what-makes-a-rule-bind}

Read what is waiting:

```bash
kapi context log --status suggested
```

```
#0n79tw5k9s  2026-09-21T19:36:17Z  agent claude-code/s8d7fb12ba4c7  correct  term "component", not "widget"  "widget" became "component"  [suggested]
  seen in docs/guide.md getting-started/p: "We utilise the widget to configure your account."
#0n791b3t34  2026-09-21T19:22:20Z  agent claude-code/s4980103f5148  observe  "The product is written \"Acme Widget\" in headings."  [suggested]
  seen in docs/guide.md: "We utilise the widget to configure your account."
```

Then decide, by the id in the first column. Any start of an id that names one
operation will do, and `keep` takes several ids at once:

```bash
kapi context keep 0n79tw5k9s
```

```
#0n79w8kr6q  2026-09-21T19:37:02Z  person  keep  of #0n79tw5k9s
  written to the project's terms store
```

Keeping writes the rule into the project's store, where every command that
reads your project's context sees it, on any branch and in any worktree. From
now on a use of the word fails a check, unless the rule is marked advisory, in
which case it reports.

Change the rule as you keep it:

```bash
kapi context keep 0n79tw5k9s --use "module" --advisory
```

Set it aside instead with `kapi context drop 0n79tw5k9s`. Either way the record stays in
the log, so the same suggestion is recognisable the next time somebody makes it.

## How a suggestion becomes a rule {#how-a-suggestion-becomes-a-rule}

Keeping is the direct way. A suggestion is also established when your own work
backs it and nothing contradicts it:

- you, or an agent recording what you changed, correct wording toward it
  (`kapi context correct widget component`);
- a change that writes its preferred form, or removes a form it avoids, reaches
  the default branch (`kapi context settle --merged`, run after a merge; see
  [the kapi loop in CI](/kapi/convergence-in-ci#settle-suggestions-after-a-merge)).

Other evidence adds to a suggestion's **standing** without establishing it:
another session recording the same rule, an agent's edit writing the preferred
form, and your content writing it, which `kapi check` over the whole project
and `kapi up` count. `kapi context log` ends each suggestion's line with its
standing as plain counts, and the context answer shows the same counts:

```
#0n79tw5k9s  ...  observe  term "Quickcast", not "Quick cast"  [suggested]  seen in 3 sessions · merged in #412
```

Evidence against a suggestion is a correction away from it, its withdrawal,
or your content moving to a form it avoids after it was recorded. Any of these
next to evidence from you makes the suggestion contested, and it waits for you
to decide. Time alone establishes nothing.

When kapi establishes a suggestion this way it records an `establish` entry
that names the evidence, and `kapi context revert` takes it back out like any
kept rule.

## When two rules disagree

Two suggestions that name different forms for one word are **contested**. Both
still advise, the log marks each `[contested by #<id>]` with the other side named,
and neither can be kept until you choose: drop the one you do not want, then
keep the other. `kapi context keep --session` leaves a contested suggestion
where it is and says so.

A suggestion that contradicts an established rule is contested too, and the
rule stays in force. When you correct wording against an established rule
yourself, the rule becomes contested: it reports instead of failing, so your
own edit never fails your build. Keep the rule again, or drop your correction,
to settle it.

## Undoing

An agent run can record a great deal in an evening. Undo all of it at once:

```bash
kapi context revert --session s4980103f5148
```

Reverting a session deactivates its suggestions and removes any rules it
established from the terms store or content memory. This restores the check
results from before the session, provided no other relevant state has changed.

Undo one operation with `kapi context revert 0n79tw5k9s`.

Nothing is erased. Reverted operations stay in the log, marked reverted.

## Where a rule holds

A rule initially applies at the context coordinates of its evidence. For
example, a term recorded in one product's reference pages does not apply to
another product's tutorials. When a profile governs where the evidence was
seen, the established rule holds only where that profile governs, and so do
the word rules in a profile's own voice or terms file under
`.kapi/profiles/<name>/` once `kapi context import` reads them.

To apply an established rule across the workspace:

```bash
kapi context widen 0n79tw5k9s --to workspace
```

That rule is then in force in every project you work on here. A project that has
its own decision about the word keeps it, because the more specific answer
always wins.

To remove a restriction on one axis while preserving the other coordinates:

```bash
kapi context widen 0n79tw5k9s --to mode
```

## Who may do what

People and agents can record observations and corrections. Only a person can
keep or drop suggestions, edit another actor's suggestion, revert an established
rule, or widen its scope. kapi rejects these operations from agents, and it
records the evidence of a merge and the rules settled on it as a tool acting
for the merge, never as an agent.

The author of a suggestion can withdraw it. An agent can withdraw only
suggestions recorded in its current session.

## How kapi knows who recorded an entry

The MCP server identifies the caller as an agent, uses the client's name and
groups its operations under one session.

For shell commands, kapi detects supported agent hosts from their environment
variables and assigns an agent identity and session automatically. An agent can
read its current session with:

```bash
kapi context log --session this
```

Three variables cover the rest.

| Variable | Says |
| --- | --- |
| `KAPI_ACTOR` | `agent` or `person`, for a shell kapi would otherwise read the other way |
| `KAPI_AGENT_NAME` | what the agent is called, for a host kapi does not recognise |
| `KAPI_AGENT_SESSION` | the id that groups this run, for the same case |

If the host provides no session identifier, kapi derives one from the process
tree so commands from the same run share a session. On Windows, where this
process information is unavailable, the default identifier covers one command.
Set `KAPI_AGENT_SESSION` to group those commands into a session.

When actor detection is uncertain, kapi uses the agent role. This keeps
suggestions subject to review and includes them in agent filters and session
reverts.

## `kapi apply` writes the same history

The asset entries of `kapi apply` are decisions about the same context, so they
appear in the same log:

```
#0n79x4m0cb  2026-09-21T19:37:31Z  person  edit  term "use", not "leverage"  [established]
  applied with `kapi apply`
```

Asset changes applied by a person are established immediately.
`kapi context import` also establishes context directly and records one
`import` operation per file.
