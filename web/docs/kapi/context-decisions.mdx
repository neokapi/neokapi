# Growing context

A new project knows nothing. It has no terms, no voice profile and no approved
wording, and it should not: the words a project cares about are the ones it
turns out to use, and nobody knows those on the first day.

Context grows out of the work instead. Someone notices how the product name is
written and records it as a suggestion. You keep it, and from then on it is an
established rule that checks hold new writing to. When you correct a
translation, that correction is evidence for the next rule.

These verbs are that loop. The first two record; the rest are the decisions.

| Verb | Does |
| --- | --- |
| `kapi context observe` | record something you noticed, such as the form the project uses for a name, with where you saw it |
| `kapi context correct` | record wording somebody changed, and the rule it implies |
| `kapi context log` | show what has been recorded and decided |
| `kapi context keep` | establish suggestions as rules |
| `kapi context drop` | set a suggestion aside |
| `kapi context withdraw` | take back a suggestion you recorded |
| `kapi context revert` | undo an operation, or everything one agent run did |
| `kapi context widen` | put an established rule in force somewhere broader |

## An agent records as it works

A coding agent with kapi's [MCP server](/reference/mcp) keeps the first two as
habits inside whatever else it is doing: `context_observe` while it reads the
project, naming the form the project uses for a word where it is consistent, and
`context_correct` the moment you change its wording. One call, one thing,
without stopping to ask you.

Everything it records is a suggestion under a **session** of its own, so you can
read a run's whole contribution in one place, keep it in one command, or undo
it in one command:

```bash
kapi context log --session s4980103f5148      # what one run recorded
kapi context keep --session s4980103f5148     # keep all of it
kapi context revert --session s4980103f5148   # undo all of it
```

It ends its report with the same session id. Nothing it recorded is in force
until you keep it.

## A suggestion never stops your work

Name the form the project uses, a form it avoids, and say where you saw it:

```bash
kapi context observe --term Quickcast --instead-of "Quick cast" --seen-in docs/guide.md
```

kapi adds the other spellings a writer reaches for: the hyphenated and
capitalised forms of a compound and the lower-case spelling of a capitalised
name, so this suggestion avoids `Quick cast`, `Quick-cast`, `QuickCast` and
`quickcast`. From that moment a check reports those forms wherever they appear.
The finding is a note. It carries no penalty, it does not lower a score, and it
cannot fail a check or a gate, not even under `--strict`. That is what makes it
safe to let an agent record suggestions while you work: whatever it suggests is
visible and nothing it suggests can break a build.

## Keeping is what makes a rule bind

Read what is waiting:

```bash
kapi context log --status suggested
```

```
#5  2026-09-21T19:36:17Z  agent claude-code/s8d7fb12ba4c7  correct  term "component", not "widget"  "widget" became "component"  [suggested]
  seen in docs/guide.md getting-started/p: "We utilise the widget to configure your account."
#2  2026-09-21T19:22:20Z  agent claude-code/s4980103f5148  observe  "The product is written \"Acme Widget\" in headings."  [suggested]
  seen in docs/guide.md: "We utilise the widget to configure your account."
```

Then decide, by the id in the first column. `keep` takes several ids at once:

```bash
kapi context keep 5
```

```
#7  2026-09-21T19:37:02Z  person  keep  of #5
  written to the project's terms store
```

Keeping writes the rule into the project's store, where every command that
reads your project's context sees it, on any branch and in any worktree. From
now on the rule bites at the severity it carries: `minor` and `neutral` report,
and anything else fails a check.

Change the rule as you keep it:

```bash
kapi context keep 5 --use "module" --severity critical
```

Set it aside instead with `kapi context drop 5`. Either way the record stays in
the log, so the same suggestion is recognisable the next time somebody makes it.

## When two rules disagree

Two suggestions that name different forms for one word are **contested**. Both
still advise, the log marks each `[contested by #n]` with the other side named,
and neither can be kept until you choose: drop the one you do not want, then
keep the other. `kapi context keep --session` leaves a contested suggestion
where it is and says so.

A suggestion that contradicts an established rule is contested too, and the
rule stays in force. When you correct wording against an established rule
yourself, the rule becomes contested: it reports instead of failing, so your
own edit never fails your build. Keep the rule again, or drop your correction,
to settle it.

## Undoing

An agent run can record a great deal in an evening. Undo all of it at once:

```bash
kapi context revert --session s4980103f5148
```

Everything that run recorded stops answering, and any rule of it you kept is
taken back out of your terms or your content memory. What a check said before
that run and what it says after the revert are the same answer.

Undo one operation with `kapi context revert 5`.

Nothing is erased. Reverted operations stay in the log, marked reverted.

## Where a rule holds

A rule holds where its evidence was seen. A word you decided about in one
product's reference pages says nothing about another product's tutorials, which
is usually what you want: house style is rarely one thing across a whole
company.

When it is one thing, say so:

```bash
kapi context widen 5 --to workspace
```

That rule is then in force in every project you work on here. A project that has
its own decision about the word keeps it, because the more specific answer
always wins.

You can also widen past a single axis of the point the rule sits at, which keeps
it specific about everything else:

```bash
kapi context widen 5 --to mode
```

## Who may do what

Anyone may say what they saw. An agent observes and records corrections, and
everything it records is a suggestion.

Deciding belongs to a person. Keeping a suggestion, editing what someone else
suggested, dropping it, reverting an established rule and widening one are all
yours. An agent that tries is refused, and told so: its tools carry no verb for
any of them.

Whoever recorded a suggestion may withdraw it, and an agent only in the session
that recorded it, which is how a run cleans up after itself.

## How kapi knows who recorded an entry

Over the MCP server the answer comes with the call: that server is serving an
agent, it has the client's name, and it groups its run under one session.

From a shell kapi reads the environment. A coding agent host puts every command
it runs into an environment of its own, and kapi recognises the common ones by
the variable each of them sets, so an agent that reaches these verbs from a
shell records as an agent, under a session, with no flag to pass. Its own run
reads back with:

```bash
kapi context log --session this
```

Three variables cover the rest.

| Variable | Says |
| --- | --- |
| `KAPI_ACTOR` | `agent` or `person`, for a shell kapi would otherwise read the other way |
| `KAPI_AGENT_NAME` | what the agent is called, for a host kapi does not recognise |
| `KAPI_AGENT_SESSION` | the id that groups this run, for the same case |

A host that names no session of its own gets one derived from its process, so
the separate kapi commands of one run share an id and a second run gets
another. Where a machine keeps its process tree out of reach, which is the case
on Windows, the id covers one command, and `KAPI_AGENT_SESSION` is how a host
says otherwise there.

kapi errs toward the agent. Reading a person as an agent costs one keep,
which the entry was heading for anyway; reading an agent as a
person would put an unreviewed rule on the record with your standing behind it,
outside `--actor agent` and beyond the reach of `revert --session`.

## `kapi apply` writes the same history

The asset entries of `kapi apply` are decisions about the same context, so they
appear in the same log:

```
#8  2026-09-21T19:37:31Z  person  edit  term "use", not "leverage"  [established]
  applied with `kapi apply`
```

They are established the moment they land, because you ran the command. The
same holds for `kapi context import`, which records one `import` per file it
reads.
