# The project store

A kapi project consists of:

- the **recipe** (`kapi.yaml`), your *config*: content, governance bindings, flows, defaults, languages;
- the **files**, your *deliverable*: the source and target files on disk;
- the **project store**, your *work*: what kapi derives from your files, plus
  the context the project works under and the decisions people record in it.

The storage model has two authoritative sources:

> **Your files are the source of truth for the deliverable, and the store is the
> source of truth for the context. Derived indexes and caches can be rebuilt.**

## What's in the store

kapi separates derived content data from authored context. The projection
database belongs to one checkout; the context database is shared by the
project's checkouts in the local workspace.

| Layer | Lives in | Kind | Lose it? |
|---|---|---|---|
| **context store** | a workspace under your data directory | **authored**: terms, voice profiles, content memory, recorded decisions | **back it up with [`kapi context export`](/kapi/context-portability)** |
| operation history | the same workspace | every observation, proposal and decision, with the evidence behind each ([Growing context](/kapi/context-decisions)) | remains local; established context can be exported |
| projection | `.kapi/work/store.db` | **derived from your files**: the block cache, the overlays a run wrote, the extraction stamps | rebuilds on the next run |
| cache | `.kapi/work/cache/` | **derived**: parse cache, extractions, collections, sync cache | rebuilds on the next run |

### The projection stays with your checkout

`.kapi/work/store.db` holds what kapi read out of the working tree: the parsed
blocks, the translations a run produced before you merged them, and the stamps
that let the next run skip a file it has already read. A second checkout of the
project keeps one of its own, because each describes the tree beside it.

### The context store sits outside your checkout

The terms, the voice profiles, the content memory and the record of who
approved what live in a **workspace** under your per-user data directory, one
database per project:

```text
<data directory>/workspaces/default/
  workspace.db          the project registry, the context graph, and the record
                        of what people and agents have recorded and decided
  projects/<key>.db     one project's terms, voice profiles, memory and decisions
```

The data directory is `$KAPI_DATA_DIR` when you set it, `$XDG_DATA_HOME/kapi`
when that is set, and otherwise the platform's own: `~/Library/Application Support/kapi`
on macOS, `%LocalAppData%\kapi` on Windows, `~/.local/share/kapi` elsewhere.
kapi creates the workspace on first use; no recipe setting is required.

`kapi init` assigns a stable project `id:`. Clones and worktrees with that id
share the local context store while maintaining separate projections of their
files. Switching branches preserves the context. Checks and context queries
use the same store, so a confirmed rule is available to the next command in
every checkout.

Use [`kapi context import`](/kapi/context-portability) to load context files
from a checkout. They affect governance only after a person imports them.

## What to commit, and what to ignore

Commit the recipe and agent configuration. `.kapi/` holds checkout-local data:
the block store, caches, redaction vault and personal reader filters. Shared
filters are kept in the project's context store. By default, `kapi init` writes
`.kapi/.gitignore` containing `*` to exclude the directory from version control.

Deletion has different consequences for each location:

- **`rm -rf .kapi/work/cache` is always safe.** Everything under it is rebuilt on
  the next run.
- **Deleting `.kapi/` removes derived data, personal filters and any redaction
  vault.** The [redaction](/framework/redaction) vault at `.kapi/work/vault/`
  contains withheld originals that are neither committed nor synced. Merge
  in-flight batches before deleting it. Workspace context is unaffected.
- **Deleting the workspace costs the context of every project on the machine**:
  the terms, the voice profiles, the content memory and the recorded decisions.
  git holds none of it, so take a copy with
  [`kapi context export --workspace`](/kapi/context-portability#backing-up-every-project-at-once)
  before you do anything that reaches your data directory.

## Repairing non-canonical locale identifiers {#rows-filed-under-an-old-language-spelling}

kapi stores and looks up locale identifiers in canonical form. Older rows may
use an identifier such as `nb_NO` that does not match a lookup for `nb-NO`,
leaving terms or approved wording absent from results. `kapi status` and
`kapi up` report these rows when detected.

```bash
kapi context locales         # inspect stored locale identifiers
kapi context locales --fix   # normalize context rows and report conflicts
```

`--fix` updates context rows in place. It changes an identifier when the
canonical key is unused and merges identical rows. Conflicting rows are
preserved and reported for manual review.

Rows in the projection are what kapi read out of your own files, so they are
rebuilt rather than moved: delete `.kapi/work/store.db` and the next `kapi up`
reads your files again.

## One context graph

The workspace keeps a graph that links a term to the blocks that use it, a
decision to the unit it approves, and both to their
[context coordinates](/kapi/context#the-context-space). A project answers graph
questions without a server: which blocks use this term, in which collection, at
which coordinate. Because the graph spans the projects you have opened, *which
projects use this concept* is a question you can ask locally too. A connected
project answers the same query shapes server-side across more dimensions. See
[C-03: The context store and graph](/contribute/architecture/context/c-03-context-store-and-graph).

## Two stages: working, then ship

The store also explains the two stages of a run:

1. **Working**: `kapi run` (with no `-o`, in a project) lands its translations
   as overlays in the block tables of `store.db`. The work is *in the store and
   not yet in your files*.
2. **Ship**: `kapi merge` writes those overlays out to the **target files**;
   `kapi status` then reads the files (plus the unit-state record) for the real ship
   state, the [kapi loop](/kapi/convergence)'s ladders and gates.

So coverage has two readings: "what's translated in the store" (working,
pre-merge) and "what's in the files and reviewed" (ship). In Kapi Desktop, the
project home's **Content** axis is the working reading; `kapi status` reports
the ship reading.

## A decision is durable the moment it is recorded

Approving a translation records a **decision** in the store, and it counts from
that moment (see [Review](/kapi/convergence#review-the-state-record)). Every
checkout of the project reads it, and there is no second step.

The decision is bound to the **content hash** of the translation and
to the source text it was approved against. Editing either drops the unit below
*reviewed*. An approval can't silently outlive the text it approved.

```bash
kapi status --review        # the worklist: units awaiting approval
kapi apply <<<'{"kind":"review","file":"src/nb.json","id":"save.label","locale":"nb","status":"reviewed"}'
kapi context log            # the decision, with the evidence behind it
```

A team that wants the record in git as well writes it there with
[`kapi context snapshot --out <dir>`](/kapi/context-portability#writing-context-out),
which puts one JSON Lines shard per document under `<dir>/state/`
([serialization](/reference/serialization/project-state)). That is a choice
about what a pull request should show.

The same model maps to a server-backed project: with the server plugin
installed, it **pushes** its decisions to a remote (`kapi push`) and **pulls**
them back (`kapi pull`), the same record with a different sink.

## An empty subsystem is an absent store

Presence is table-level. A context store whose terms tables are empty behaves
exactly as though there were no terms store at all: the terminology gate
enforces nothing, `kapi up --plan` never creates state, and `kapi pack` carries
only the parts that hold something. Only populated subsystems contribute context.

The same model runs in the browser, where everything is held in memory and the
decisions persist to a sidecar file beside the projection. A browser tab holds
one project and nothing outlives it, so it keeps its context beside its
projection rather than in a workspace.

## What the store is *not*

- The **content memory** in it is a recycle corpus rather than a review record:
  `kapi apply` with `kind:"memory"` adds leverage for future translation and
  records no review. A review outcome is a decision. See
  [Memory & terms storage](/kapi/recipes/memory-and-terms-storage).
- It is **not** authoritative for your translations; the **files** are. The store
  indexes what the files hold; the deliverable is the source of truth.
