# Moving context

A project's context is the terms it has agreed on, the voice profiles that
govern how it writes, the wording it has already approved, and the record of who
approved what. It lives in your [workspace](/kapi/project-store) on this
machine, one store per project, and every clone, worktree and branch of the
project reads that one store.

Four verbs carry it in and out of that store as files.

| Verb | Moves | Use it to |
| --- | --- | --- |
| `kapi context import` | a checkout's files → store | bring an existing project's context in |
| `kapi context snapshot` | store → files | put a copy in git, or hand it to a clean clone |
| `kapi context export` | store → one file | back the context up, or carry it to another machine |
| `kapi context restore` | one file → store | put a backup back, here or somewhere else |

Export and restore also take `--workspace`, which carries every project you work
on here rather than the one in front of you. See [backing up every project at
once](#backing-up-every-project-at-once).

Import and snapshot are the two directions between a directory of files and the
store. Export and restore are the same two directions against a single archive.

## What counts as context

The same four things everywhere, each with the file shape a snapshot writes it
in and an import reads it from:

- **terms**: the concepts and the approved word for each, per language
  (`terms.json`);
- **voice profiles**: the project default and one per profile that overrides it
  (`voice.yaml`, `profiles/<name>/voice.yaml`);
- **content memory**: the source and target pairs already produced and reviewed
  (`memory/*.memory.json`);
- **the decision record**: who approved which wording, against which text
  (`state/*.jsonl`).

Your content files stay in git, and a project's context is about them rather
than a copy of them.

## What never travels

Redaction withholds sensitive values before content reaches a model or a
service, and keeps the originals in a vault on the machine that read them
(`.kapi/work/vault/`). That vault is excluded from a snapshot and from an
export, and there is no flag that puts it in either. If you move a project to
another machine, the placeholders come with it and the originals do not.

The rest of `.kapi/work/` is excluded too. Everything there is what kapi read
out of your own files, rebuilt on the next run, and none of it is context.

The record of how the context got there stays where it is as well: every
observation, proposal and decision with its evidence
([Growing context](/kapi/context-decisions)) belongs to this computer's
workspace. What travels is the context those decisions produced.

## Reading context in

```bash
kapi context import
```

```
Read .kapi into the project store:
  1 concept
```

This is the one command that opens a context file. Everything else answers from
the store, so what you read here is in force for every checkout of the project
on this machine, and for everyone else once they run it too.

A person runs it. Reading a checkout's files puts them in force for everyone
working in the project, which is a decision rather than a step in a script, so
kapi refuses the same command from a coding agent and names what to ask for:

```
Error: agent claude-code/s4980103f5148 may not import context: reading a
checkout's context files puts them in force for everyone working in this
project, which a person decides: ask the person working here to run
`kapi context import`: refused by the context policy
```

With no path it reads the project's own `.kapi/` directory. Name a directory to
read another checkout's context instead:

```bash
kapi context import ../old-project/.kapi
```

That is the way in for a project whose context was authored as files, and the
way a team hands its context to somebody starting fresh.

Each file read is recorded with its digest, so `kapi context log` says which
files the store was built from and when:

```
#7  2026-09-22T07:23:03Z  person  confirm  note "content-memory bundle .kapi/memory/memory.json, 0 entries"
  seen in .kapi/memory/memory.json: "sha256:f89b91fdca8829b705701266d75fb796d11f8549e3634158adf0d23883794e7d"
#6  2026-09-22T07:23:03Z  person  confirm  note "terms bundle .kapi/terms.json, 1 concept"
  seen in .kapi/terms.json: "sha256:ef9b7f79f21235d1065dca333930ddd44147c19e3d134e640a941ef044de3c09"
```

Reading twice changes nothing. Every concept, entry, profile and decision is
matched by the identity it already carries, so a second read finds the store
already holding what the file says:

```
Nothing to read: 2 sources already in the store at these bytes.
```

A file whose bytes have not moved since this checkout read it is skipped;
`--force` reads it anyway.

## Meeting a project whose context is still in files

A clone that arrived carrying context files, against a store that has never
held this project, gets one line on standard error from every command that
resolves the project:

```
note: this project carries context files (.kapi/memory/memory.json, .kapi/terms.json) and its store holds no context yet. They are read by `kapi context import`, and until then nothing in them is in force
```

`kapi check` carries the same line as a configuration warning, which never
changes the score, the gate or the verdict:

```
Configuration warnings (1):

  code            location  message
  context.unread  .kapi     this project carries context files (.kapi/memory/memory.json, .kapi/terms.json) and its store holds no context yet. They are read by `kapi context import`, and until then nothing in them is in force
  Warnings are separate from findings: they never change the score, the gate or the verdict.
```

Kapi Desktop shows it on the project and on the workspace home, and the MCP
surface carries it on the context resource, so an agent reading the project can
tell you what to run. The notice stops once the store holds anything at all.

## Writing context out

```bash
kapi context snapshot --out build/context
```

This writes, into the directory `--out` names, the layout `kapi context import`
reads: `terms.json`, `memory/memory.json`, each voice profile at the path the
recipe binds it from, and the decision record's shards. `--out` is required:
`.kapi/` is a cache for one checkout, so a snapshot goes where you say. A team
that keeps its snapshot in `.kapi/` names it (`--out .kapi`) and commits it under
an ignore rule of its own.

The files it writes are **generated**. Each voice profile it creates says so at
the top of itself. Change the project's context and snapshot again rather than
editing them, the way you would with any other generated artifact.

Three properties make a snapshot usable as a reviewed artifact:

- **It does not churn.** A snapshot with nothing to say writes nothing, so it
  leaves no diff and no modification times behind.
- **It round-trips.** Read a snapshot into a project with no store and snapshot
  again, and you get the same bytes.
- **A clean clone governs the same way after one command.** Run
  `kapi context import` in a checkout holding a snapshot, and it resolves the
  same voice, the same terms and the same rules the project that wrote the
  snapshot resolves.

The decision record in a snapshot is the project's own, written from what the
store holds at the moment of the snapshot. It is the way a team that wants its
approvals reviewable in git gets them there, and that is a choice each team
makes rather than something kapi needs.

A directory that already holds content-memory bundles you wrote by hand keeps
them. A snapshot writes the store's own bundle beside them rather than deleting
files it did not write. To get a directory holding only the snapshot, point
`--out` at a fresh one.

## Packing it into one file

```bash
kapi context export -o context.kpz
```

One file holding everything above. It is the backup a store that holds reviewed
work needs, and the way to carry a project's context to another machine. Nothing
is flattened on the way: every part travels in the form kapi reads it back from,
so a restore puts it into a store with the identities it left with.

```bash
kapi context restore context.kpz
```

Restoring into a project whose store already holds context stops and asks which
you meant:

```bash
kapi context restore context.kpz --merge     # read it over what is there
kapi context restore context.kpz --replace   # put it in place of what is there
```

`--merge` is idempotent, like an import: restoring the same file twice leaves
the same store. `--replace` empties the context stores first, so what is left is
the file and nothing else.

A file written by a later kapi than the one reading it is refused by name, with
the version that could not read it, rather than read halfway.

### Every branch's approvals, not just the one you are on

Checkouts of one project share its decisions, and two of them on different
branches can answer the same sentence differently. An export carries both.
Restoring it puts both back, and each checkout then answers with the approval
made against the text it actually holds, so a backup taken on one branch keeps
what was approved on another. A snapshot writes the shards for the branch you
are on, because that is the text the checkout under it holds.

## Backing up every project at once

Your projects share one place for their context on this computer, and git does
not track it. Losing it loses the terms, the voice profiles, the approved
wording and the recorded decisions of every project you work on here. Two flags
back up the whole of it.

Start by seeing what you have:

```bash
kapi context export --workspace --dry-run
```

That writes nothing. It lists every project, what its context holds, and which
of them still have a working copy on this computer. Then write the file:

```bash
kapi context export --workspace -o everything.kpz
```

A project travels whether or not you still have it checked out here, which is
the point: a repository you deleted a year ago keeps the terms and approvals it
earned, and they come back with it. Each project inside the file is a complete
context file of its own, so unzipping the backup gives you one `.kpz` per
project that `kapi context restore` reads on its own.

Reading it back needs no checkouts at all:

```bash
kapi context restore --workspace everything.kpz
```

Every project comes back under the name and identity it had. Clone a repository
afterwards and the first command you run there finds its context waiting.

A computer that already has projects of its own stops and asks which you meant,
the same way a single project does:

```bash
kapi context restore --workspace everything.kpz --merge     # read it over what is there
kapi context restore --workspace everything.kpz --replace   # put it in place of what is there
```

`--replace` lists every project whose context it is about to empty before it
empties any of them, so a backup aimed at the wrong computer is something you
read rather than something you discover.

Withheld originals are not in a workspace backup either, and neither are the
directories your projects live in. Those name folders on one computer and mean
nothing on the next.

## Which one to use

- Bringing an old project in, or picking up a clone that arrived with context
  files: **import**.
- Putting a copy of the context in a pull request, or giving somebody the files
  their own import will read: **snapshot**.
- A backup before a risky change, or moving a project between machines:
  **export**, then **restore**.
- Everything you have worked on here, before a reinstall or a new laptop:
  **export `--workspace`**, then **restore `--workspace`**.
