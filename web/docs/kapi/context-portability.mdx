# Moving context

A project's context includes terms, voice profiles, content memory and approval
records. It lives in your local [workspace](/kapi/project-store), with one store
per project shared by its clones and worktrees. Every change to it is recorded
as an operation, and these commands move those operations between machines.

| Verb | Moves | Use it to |
| --- | --- | --- |
| `kapi context pull` | backend → this machine | take in what the rest of the team recorded |
| `kapi context push` | this machine → backend | share what you recorded |
| `kapi context export` | this machine → one file | back the context up, or carry it where no backend reaches |
| `kapi context import <file>.kpz` | one file → this machine | merge such a file, the way a pull does |
| `kapi context import [dir]` | context files → this machine | bring in terms, voice profiles and records authored as files |

## What counts as context

Everything a project records about how its content is written travels: the
suggestions and their evidence, the decisions a person made about them, the
terms, the voice profiles, the approved wording in the content memory and the
record of who approved which translation. A pull merges them by operation, so
two machines that recorded different things both keep what they recorded.

Content files are managed separately in git.

## What never travels

Redaction withholds sensitive values before content reaches a model or a
service, and keeps the originals in a vault on the machine that read them
(`.kapi/work/vault/`). The vault is never pushed and never exported, and there
is no flag that changes that. If you move a project to another machine, the
placeholders come with it and the originals do not.

Rules you widened to every project stay on your machine too: they belong to
your workspace, not to the project. The derived stores and caches under
`.kapi/work/` are rebuilt from your content files.

## Sharing context through a backend

Declare where the project's context is shared in `kapi.yaml`:

```yaml
context:
  backend: git                  # local (the default), file, git or s3
  ref: refs/kapi/context        # git: a ref in this repository, outside every branch
```

| Backend | Keeps the context in | Recipe fields | Access |
| --- | --- | --- | --- |
| `git` | a ref of the project's own repository | `ref` (default `refs/kapi/context`), `remote` (default `origin`) | the repository's own: whoever can push a branch can push the ref |
| `file` | a directory, such as a mounted team share | `path` | the filesystem's |
| `s3` | an S3-compatible bucket | `bucket`, `prefix`, `region`, `endpoint` | the standard AWS environment, shared configuration and profile |

Credentials never go in the recipe. Then pull before you work and push when you
are done:

```bash
kapi context pull
```

```
Pulled 3 operations from git origin refs/kapi/context in 0.1s.
Context: 0 to push, 0 to pull (as of 2026-09-26 10:03).
```

```bash
kapi context push
```

```
Pushed 3 operations to git origin refs/kapi/context in 0.2s.
Context: 0 to push, 0 to pull (as of 2026-09-26 10:03).
```

Each machine only ever adds files of its own to the backend, so two people
pushing at once both succeed, and a pull reads only what this machine has not
seen. `kapi status`, `kapi context <path>` and the context an agent reads end
with the same line, counted at the last pull or push, so you know when there is
something to share or take in.

A git backend is fetched explicitly: a clone fetches branches and tags, and
`kapi context pull` fetches the ref itself. A fork's pull request can pull the
context and cannot push it.

When the backend cannot be reached, nothing changes and the command exits with
status 5:

```
Error: workspace: the context backend could not be reached: git fetch origin refs/kapi/context: ...
Nothing changed here. 1 operation waits to be pushed; run `kapi context push` again when the backend is reachable
```

### Using another backend on one machine

`kapi context backend` shows which backend is in force and where that was
decided. Name one to use it on this machine only, without editing the recipe:

```bash
kapi context backend local                          # keep this project's context here
kapi context backend file /Volumes/team/kapi/docs   # share it through a directory
kapi context backend recipe                         # use what kapi.yaml declares again
```

The choice is kept in this machine's kapi configuration under the project's id.

## Reading context in

```bash
kapi context import
```

```
Read .kapi into the project store:
  1 concept
```

Import loads context files into the store shared by this project's local
checkouts, and a push shares what it read with everyone else.

Only a person can import context. kapi rejects an import attempted by an agent
and reports the command for the person to run:

```
Error: agent claude-code/s4980103f5148 may not import context: reading a
checkout's context files puts them in force for everyone working in this
project, which a person decides: ask the person working here to run
`kapi context import`: refused by the context policy
```

With no path it reads the project's own `.kapi/` directory. Name a directory to
read another checkout's context instead:

```bash
kapi context import ../old-project/.kapi
```

That is the way in for a project whose context was authored as files, and the
way a team hands its context to somebody starting fresh.

Each file read is recorded with its digest, so `kapi context log` says which
files the store was built from and when:

```
#0n8j90rfyb  2026-09-22T07:23:03Z  person  import  "content-memory bundle .kapi/memory/memory.json, 0 entries"  [established]
  seen in .kapi/memory/memory.json: "sha256:f89b91fdca8829b705701266d75fb796d11f8549e3634158adf0d23883794e7d"
#0n8j901rwk  2026-09-22T07:23:03Z  person  import  "terms bundle .kapi/terms.json, 1 concept"  [established]
  seen in .kapi/terms.json: "sha256:ef9b7f79f21235d1065dca333930ddd44147c19e3d134e640a941ef044de3c09"
```

Import is idempotent: concepts, entries, profiles and decisions are matched by
identity. Repeating an import of unchanged files leaves the store unchanged:

```
Nothing to read: 2 sources already in the store at these bytes.
```

Unchanged files are skipped. Use `--force` to read them again.

## Meeting a project whose context is still in files

If a checkout contains context files but its project store is empty, commands
that resolve the project print this notice to standard error:

```
note: this project carries context files (.kapi/memory/memory.json, .kapi/terms.json) and its store holds no context yet. They are read by `kapi context import`, and until then nothing in them is in force
```

`kapi check` carries the same line as a configuration warning, which never
changes the score, the gate or the verdict:

```
Configuration warnings (1):

  code            location  message
  context.unread  .kapi     this project carries context files (.kapi/memory/memory.json, .kapi/terms.json) and its store holds no context yet. They are read by `kapi context import`, and until then nothing in them is in force
  Warnings are separate from findings: they never change the score, the gate or the verdict.
```

Kapi Desktop shows it on the project and on the workspace home, and the MCP
surface carries it on the context resource, so an agent reading the project can
tell you what to run. The notice stops once the store holds anything at all.

## Carrying context in one file

```bash
kapi context export -o context.kpz
```

```
Wrote 3 context operations to context.kpz (8.2 KiB).
```

The file holds the project's whole context with its history: the same files a
backend keeps, and a checkpoint so reading it back is fast. It is the backup,
and the way to carry a project's context to a machine no backend reaches.

```bash
kapi context import context.kpz
```

`import` merges the file the way `pull` merges a backend: every operation this
project does not hold is added, and reading the same file twice changes nothing
more. A file holds one project's context, and importing it into a checkout of
another project is refused with both names.

## Which one to use

- Working on a project with other people, or on more than one machine: declare
  a **backend**, then **pull** and **push**.
- A backup before a risky change, or a machine the backend does not reach:
  **export**, then **import** the file.
- Bringing an old project in, or picking up a clone that arrived with context
  files: **import** the directory.
