# Keep your writing consistent, and check every edit

A help article, an API reference and a release note should use the same words,
whoever writes them. kapi reads the files in your project and holds the rules
the project keeps: its terms, its voice, and the suggestions a person decided to
keep. Before you or an agent writes, `kapi context <path>` says what applies to
that file. After the edit, `kapi check` fails when a finding fails. None of it
needs linguistic training, and all of it works in a project with one language.

[Start a project](/kapi/get-started/first-project) or
[use kapi with your agent](/kapi/get-started/use-with-claude).

## See what applies

`kapi look` prints the project at a glance: its files, the blocks in them, the
rules in force, the findings a check reports and the suggestions waiting for
you. `kapi look <path>` prints one file's blocks with each finding marked
under the words it is about, and the rules that hold there.

`kapi context <path>` prints the rules that apply to one file as the text an
assistant reads: the voice, the words to use and to avoid, and what has been
suggested but not yet decided.
`kapi init` also writes these rules into a section of `AGENTS.md` and
`CLAUDE.md`, which an agent loads as it starts, and kapi rewrites that section
when the rules change. In Kapi Desktop, a project's **Context** pages show the
same rules: **What's new**, **Ask** for one file, **Voice** and **Terms**. See
[Context](/kapi/context).

## Decide what becomes a rule

An agent records what it notices with `kapi context note`, such as how the
project spells its product or a wording you changed in its draft. Each note
arrives as a suggestion. Checks report a suggestion and never fail on it. A
person decides with `kapi rules`, which asks about each suggestion with the
evidence and the blocks it would affect, or with **Keep**, **Change** and
**Drop** under **What's new** in the desktop, and a suggestion that person
keeps becomes a rule that fails a check.

The **terms store** holds the word rules: a term, what to use instead, and the
concepts the project agrees on. The **voice profile** holds tone, style
measures and pattern rules, and the recipe binds it with `defaults.voice`. A
rule kept with `--advisory` reports its findings and never fails a check. See
[Growing context](/kapi/context-decisions).

## Check every edit

`kapi check <file>` runs the configured checks and prints each finding with
its rule id. It exits `3` when a finding fails, so the same command gates CI,
and `kapi check --ship` enforces the project's release policy. The kapi plugin
for Claude Code adds a Stop hook that runs `kapi check --ship` when the agent
tries to finish and keeps it working while a gate fails. `kapi fix` applies the
replacement each failing word-rule finding names, through the change service
`kapi apply` uses, and lists the findings that need a rewrite.

A passing check means the configured checks met their thresholds. Factual
accuracy and overall quality need their own review. See
[Check content like tests](/kapi/recipes/verify-content) and the
[check reference](/reference/checks).

## Add languages when you need them

Add a target language to the recipe when the project needs one. `kapi up` then
translates changed content into each language, reuses earlier translations
from the content memory, and holds back what needs a person for review.
`kapi translate` translates a single file. See
[Add languages](/kapi/get-started/add-languages) and
[the kapi loop](/kapi/convergence).

In the installed kapi, the language commands appear in `kapi --help` once the
recipe declares a target language. Before that, `kapi help languages` lists
them.

## The engine underneath

kapi runs on the open neokapi content engine. Format readers extract each file
into blocks, tools process the blocks, flows chain tools, and format writers
put the edits back with the structure around the text kept. Formats differ in
what they preserve; the [format evidence](/format-maturity) shows what holds
for each. `kapi help --all` lists every command, including the engine's. See
[Framework](/framework/architecture).

## Three ways to run it

The CLI, your agent and Kapi Desktop work on the same
[kapi projects](/reference/project-file), so a rule kept in one holds in the
others:

- **Kapi CLI**: one binary that operates on files, for scripts and CI.
- **Your agent**: `kapi connect` writes the rules into `AGENTS.md` and
  `CLAUDE.md`, adds the kapi skill and an MCP server entry, so the agent you
  already use reads the rules and runs the checks. See
  [Use with your agent](/kapi/get-started/use-with-claude).
- **Kapi Desktop**: an app where you read the rules a project keeps, decide
  about what your assistants noticed, and check the project's files, with no
  YAML and no flags. `kapi open` opens the folder you are in there. See the
  [Kapi Desktop overview](/kapi/desktop/overview) and
  [CLI or Desktop?](/kapi/get-started/cli-vs-desktop)
