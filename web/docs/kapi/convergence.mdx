# Convergence

Source content changes and its translations fall behind; kapi treats catching
up as a project's normal state, not an error. **Convergence** is the model that
drives content toward *shippable* and reports what still needs a person —
without ever blocking the author.

Three verbs, kept separate:

- **Convergence produces** — it drives each unit as far up its lifecycle as a
  flow can take it unaided (typically to *translated*).
- **Review promotes** — a person advances a unit past what a machine can decide
  (*translated → reviewed*).
- **The gate releases** — it drives nothing; it answers one question, *is this
  scope shippable?*

## State is derived, not tracked

Kapi stores no workflow state — no "in progress" flags, no cursors. Every command
**recomputes** a unit's state from the content on disk and the project's assets,
the way `git status` recomputes from the working tree. Run a command twice with
no changes and you get the same answer; change a source file and the affected
units fall back to *pending* on their own.

The unit of state is a **target**: one translatable block in one locale.

## The lifecycle ladders

A target climbs a monotone ladder — each rung implies the ones below it. An
absent target sits below the lowest rung; a present, non-empty target is at least
*translated*.

Where state is recorded depends on the carrier. A plain target file (JSON, an
XLIFF, …) records presence only, so a file-based project reads a present target
as *translated*. The higher rungs ride a carrier that can hold them: *reviewed*
comes from an approved decision in the project's
[state store](#review-a-decision-in-the-project-state-store) (below), and a `.klf`
parcel carries the full status across a hand-off.

## The gate — coverage thresholds

A **gate** is a set of coverage thresholds over the ladder: a state name to a
minimum percent. A scope clears a gate when, for every threshold, at least that
percent of its units have reached that rung or higher.

```yaml
# my-app.kapi
ship_gate: { translated: 100, reviewed: 80 }
```

This reads *"every unit translated, and the important 80% reviewed — ship the long
tail machine-translated."* A bare `100% reviewed` is the degenerate case.

Gates can be selected by rule (`ship_gates:` with `when:` clauses), so a
contractual locale can answer to a stricter bar than the default — the most
specific matching rule wins; see the
[project file reference](/reference/project-file). The source ladder has its own
optional bar, `source_gate` (e.g. `{ checked: 100 }`). A gate never fails an
ordinary build — target drift is expected work; a gate is a **release** check
you opt into (below).

## Seeing it: `status` and `check --ship`

`kapi status` is the derived dashboard — coverage per locale and each scope's
standing against its gate, recomputed on every run:

```bash
kapi status
# source: 2 units  authored 100%  checked 0%  approved 0%
#
# scope    units   draft  translated  reviewed  signed-off  ship
# de          42    100%        100%       80%         0%  ✓ shippable
# nb          42    100%         60%        0%         0%  pending (translated 60%<100%)
```

`kapi check --ship` is the enforcing counterpart — it runs the project's bound
quality gates (brand, terminology, QA) plus the ship and source coverage gates
as a pre-release bar (a failing gate exits non-zero, for a release tag or a
`main` check). Ordinary `kapi check` stays file-scoped and non-blocking about
coverage. See [Ship gates & CI](/kapi/recipes/gate-localization-in-ci).

## Convergence: `kapi up`

A flow is one linear pass. *Convergence* is that pass looped to the gate — and
`kapi up` is that loop as a verb. It runs the project's default flow
(`defaults.flow`) over all content across every target language, re-deriving
coverage between passes, until every gated scope is shippable or parked:

```yaml
defaults:
  flow: translate-and-check   # a flow defined under flows:
```

```bash
kapi up                # loop the default flow until each scope ships, or parks
kapi up --passes 1     # a single pass (the behavior of the bare 'kapi run')
```

Each pass re-derives coverage and runs again on what is still short — until
every gated scope is shippable, a pass makes no progress, or the pass cap
(`--passes`, capped at 5) is reached. Whatever cannot be advanced unaided
**parks**: it is reported as awaiting a human and the command still exits zero.
Convergence never blocks the author.

`kapi up --plan` is the dry run — pending work, TM leverage, and a token
estimate per (collection, locale), with no provider calls. One default flow can
still vary by locale: `defaults.locales.<lang>.tools` overrides a tool's config
for one target language (see the
[project file reference](/reference/project-file)).

## Review: a decision in the project state store

A machine takes a unit to *translated*; a person takes it to *reviewed*. That
approval is a workflow **decision** — who signed off on which exact translation —
so it lands in the project's [state store](/kapi/project-store), the committed
carrier of decisions (`defaults.state`, default `.kapi-state.json`), not the
translation memory.

`kapi status --review` is the worklist — every translated unit not yet approved —
and you approve a unit with the one write verb, `kapi apply`, as a `review`
change-set addressed by the unit's `file` / `id` / `locale` exactly as the worklist
lists them:

```bash
kapi status --review        # the worklist: file, id, locale per pending unit
kapi apply <<<'{"kind":"review","file":"src/nb.json","id":"save.label","locale":"nb","status":"reviewed"}'
```

The decision is bound to the **content hash** of the translation it blesses, so
editing that translation afterwards drops the unit back below *reviewed* — an
approval can't silently outlive the text it approved. Once recorded, coverage reads
the unit as *reviewed*, `reviewed%` climbs, and a `{ reviewed: … }` gate flips to
shippable. The state file is committed with your sources, so the decision travels
with the project (a server-backed project pushes it to a remote instead).

This is distinct from the translation memory: `kapi apply` with `kind:"tm"` adds a
source→target pair to the **recycle** corpus (`defaults.tm_source`) for future
leverage — it does **not** promote a unit to *reviewed*.

A second, optional human gate sits above review: *signed-off* — a final approval
for content that needs it (a contractual locale, a regulated string), recorded
the same way with a `signed-off` status; it is the top rung a
`{ signed-off: … }` gate measures. In Kapi Desktop the whole ladder is the
[Review surface](/kapi/recipes/review-and-approve) — queue, editor,
approve/reject, sign-off.

the memory and termbase model, and [Keep source on brand](/kapi/recipes/keep-source-on-brand)
for the source-side checks that drive the authoring ladder.
