# Use with Claude

Run `kapi connect` in the project's folder to put Claude, or another assistant,
on the project. The sections below say what it writes and why, then how to set
the same up by hand. In the other direction, kapi can run Claude through your
Claude Code sign-in; see [Let kapi run Claude](#let-kapi-run-claude).

## Connect an assistant

```text
$ kapi connect
Claude Code   connected · rules, MCP server, skill
  .mcp.json            created
  .claude/skills/kapi  created
  Stop hook            pending: in Claude Code, /plugin marketplace add neokapi/claude-plugins, then /plugin install kapi@neokapi-plugins
Cursor        connected · rules, MCP server
  .cursor/mcp.json     created
VS Code       not connected: no .vscode/ folder here (kapi connect vscode adds it)
Codex         not connected: no .codex/ folder here (kapi connect codex adds it)

Project
  kapi.yaml            created
  AGENTS.md            created
  CLAUDE.md            updated (Writing rules section)

See what an assistant reads for a file: kapi context <path> --explain
```

That run was in a folder with a `.cursor/` directory, a `CLAUDE.md` of its own
and no recipe. `kapi connect` connects Claude Code and each assistant whose
folder the project keeps, and lists the others. Each line says what happened:
created, updated or kept for a file; deleted, or removed the section, for a
rules file in a folder that has no rules of its own any more. A folder with no
recipe gets the one `kapi init` writes. A second run keeps every file as it is.

- `kapi connect --dry-run` lists the same files with what it would do, and
  writes none of them.
- `kapi connect codex` connects one assistant: `claude`, `cursor`, `vscode`,
  `codex` or `agents`. Any other name exits with status 1 and lists these.
- `kapi connect --json` gives the assistants and the files as data.

`kapi init` writes the same files when it creates a project, so a project made
with `kapi init` is already connected to Claude Code. Running `kapi connect` is
how a project created earlier gets the current wiring.

## What it wrote, and why

An assistant on a kapi project meets the rules at three points: as it starts,
before it writes, and after it edits.

**As it starts**, it reads the Writing rules section of `CLAUDE.md`, the file
Claude Code reads, or of `AGENTS.md`, which most other agents read: the voice,
what to write and what not, and the `kapi check` line. A folder whose rules
differ from the root's gets files of its own, so a rename kept for `help/` is
stated in `help/CLAUDE.md`, and `api/CLAUDE.md` says the old name is correct
there. kapi rewrites the section when the rules change and leaves the rest of
each file as you wrote it; a `CLAUDE.md` that imports `@AGENTS.md` gets no
section of its own. See [rules files for agents](/kapi/context#rules-files).

**Before it writes** a file the section does not cover, it asks
`kapi context <path>`, or `context_read` through the MCP server.
`kapi context <path> --explain` prints what it reads there.

**After it edits**, it runs `kapi check` on each file it changed, or
`check_file`, and fixes what fails. The Stop hook in the kapi Claude Code
plugin runs the project gate (`kapi check --ship`) when Claude tries to finish,
and keeps it working while a gate fails. `kapi connect` reports the hook as
pending until the plugin is installed and enabled, with the two commands that
install it.

As it works, the assistant notes what the files keep to and what you change in
its drafts, with the file and sentence each came from. Each note arrives as a
suggestion: checks report it and none fails on it until you keep it with
`kapi rules`. A note holds only in the files where the assistant saw it until
you widen it. See [Growing context](/kapi/context-decisions).

### What `kapi connect` writes {#what-kapi-init-wires-up}

| Agent | What it gets |
|---|---|
| **Claude Code** | `.mcp.json` with the `kapi` server, and the kapi skill in `.claude/skills/kapi/SKILL.md` |
| **Cursor** | `.cursor/mcp.json` with the `kapi` server |
| **VS Code** | `.vscode/mcp.json` with the `kapi` server |
| **Codex** | `.codex/config.toml` with the `kapi` server, read once you trust the repository |
| **Any SKILL.md-aware tool** | the kapi skill in `.agents/skills/kapi/SKILL.md` |

Every agent also gets the rules files. The skill says how to read what applies
to a file, note what it sees and what you change, check edits, and report the
session, with the CLI and MCP form of each. `kapi help <topic>` prints the
longer guides from your installed binary.

Claude Code is wired every time. The others are wired when the project already
keeps their directory, so neither command adds a directory for an editor you do
not use. Name one with `kapi connect <assistant>`, or choose with
`kapi init --agents`:

```bash
kapi init --agents claude-code,cursor   # exactly these
kapi init --agents all                  # every agent kapi knows
kapi init --agents none                 # write no agent configuration
```

`kapi init --no-rules-files` leaves out the rules files.

Everything it writes is inside the project, and the MCP entry holds a command
and nothing else: no shell, no environment, no credential. An entry called
`kapi` that you wrote or changed is left exactly as it is. An entry exactly as
kapi wrote it follows the recipe, so after you add target languages, running
`kapi connect` again adds the translation tools. A skill directory an earlier
kapi filled with reference files is cleared of the files kapi wrote there, and
any file of yours in it stays.

Claude Code asks you to approve a project MCP server the first time you open the
project, so review `.mcp.json` before you say yes, the way you would any file a
repository ships.

## Set it up by hand

These are the pieces `kapi connect` writes, for a client it does not configure
or a setup you want to control yourself. All of them need `kapi` on your `PATH`
([installation](/kapi/get-started/installation)), and none needs a provider
credential for attended work: Claude writes, kapi applies and checks.

| You work in… | Use | How it reaches kapi |
|---|---|---|
| **Chat** (Claude Code, plain-language prompts) | the **Agent Skill** (`SKILL.md`) | Claude runs `kapi` commands itself and loops until the checks pass |
| **IDE** (Claude Desktop, Cursor, Windsurf, VS Code) | the **MCP server** (`kapi mcp`) | `context_read` for a file the rules files do not cover, `context_note` for what it notices, and `check_file`; `--tools` adds [more sets](/reference/mcp#available-tools) |
| **CI** (no assistant in the loop) | the **CLI** directly | `kapi check` / `kapi check --ship` exit non-zero, failing the build |

<details>
<summary>Install the Agent Skill (Claude Code and any SKILL.md-aware tool)</summary>

**Claude Code**: the plugin bundles the skill plus two hooks:

```text
/plugin marketplace add neokapi/claude-plugins
/plugin install kapi@neokapi-plugins
```

The **Stop hook** is the one described above. The **PreToolUse hook** denies
hand-edits to generated translation targets, steering changes through the
source. Both are fail-open outside a project, and both follow one
[decision protocol](#the-hook-decision-protocol). `kapi connect` reads the
project's `.claude/settings.json` and `.claude/settings.local.json`, then your
own Claude Code settings (`settings.json` in `$CLAUDE_CONFIG_DIR`, or in
`~/.claude`), and reports the hook as kept once one of them enables the plugin,
or `kept (enabled for your user)` when only your own settings do.

**Copilot, Cursor, Windsurf, VS Code, Codex**: `SKILL.md` is an open standard:

```bash
npx skills add neokapi/agent-skills --skill kapi     # add -a <tool> for a specific tool
npx skills update kapi                               # refresh later
```

</details>

<details>
<summary>Install the MCP server (Claude Desktop, Claude Code, Cursor, and the rest)</summary>

Your client launches `kapi mcp` as a stdio subprocess. Claude Code and Cursor read the server list under `mcpServers`; VS Code reads it under `servers`. Claude Desktop uses `claude_desktop_config.json` with the same shape as Claude Code's:

```json
{
  "mcpServers": {
    "kapi": {
      "type": "stdio",
      "command": "kapi",
      "args": ["mcp", "--project", "kapi.yaml"]
    }
  }
}
```

`--project` names the project the server answers for, so it binds yours rather than whichever project sits above the directory your client started it in. The writing tools include `read_blocks`, `apply_edits` and `describe_format`, which read a file's blocks, write edits back with the file's structure and inline codes kept, and say what a format supports. For a project that declares target languages, `kapi connect` and `kapi init` add `"--tools", "writing,translation"` to the arguments, so the agent also gets the translation tools beside the writing ones.

See [MCP server](/reference/mcp) for every client's configuration and the full tool list.

</details>

### The hook decision protocol {#the-hook-decision-protocol}

A kapi hook states its verdict as JSON on stdout and always exits `0`. The verdict travels on stdout rather than in the exit code: Claude Code reads a non-zero exit as a *broken hook*, so a denial carried that way would be downgraded to a hook error rather than enforced. `kapi check --ship` keeps its own gate exit code (`3`) when you run it yourself; the hook drives that gate without replacing it.

| What the hook found | On stdout | What happens |
|---|---|---|
| A gate fails / the file is a generated target | `{"decision":"block","reason":"…"}` (Stop) · `{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":"…"}}` (PreToolUse) | Claude keeps working, or the edit is refused. The `reason` names the findings, or the source and locale to change instead. |
| Nothing to report (gates pass, the file is not generated, or there is no kapi project) | nothing | The operation proceeds. |
| **The guard could not run at all** | `{"systemMessage":"…"}` plus the same warning on stderr, naming the hook | The operation proceeds: kapi hooks fail open, so a broken guard never blocks work. But the bypass is stated, because a guard that never ran must not look like a guard that passed. |

An unreadable, empty, or malformed hook payload; a session directory kapi cannot enter; a recipe that will not load because it needs a plugin you have not installed: each of those leaves the guard installed but inert. The notice says which hook, and what stopped it.

The wire shapes are Claude Code's, and Claude Code versions its own hook schema; kapi does not add a version of its own. What is stable here is the policy in the table: fail open, and report the bypass.

## Let kapi run Claude

For unattended runs (`kapi up` across every locale, `kapi translate` without you in the loop) kapi needs a provider of its own. If Claude Code is signed in on your machine, that provider can be your Claude subscription:

```bash
kapi models setup     # detects the Claude Code CLI ("uses your Claude subscription"): one confirm, no key
```

| You have… | Use |
|---|---|
| **Claude Pro or Max** (Claude Code installed) | `kapi models setup`, and kapi runs Claude on your subscription with no key. |
| **An API key** (Anthropic, OpenAI, Gemini) | `kapi models setup` finds keys already in your environment, or stores one in the OS keychain, and verifies it with a test call. |
| **Nothing, or offline** | A local model via [`kapi models ollama`](/kapi/recipes/choose-a-translation-provider), or Kapi Desktop's demo engine (illustrative output, no AI). |

Setup verifies the choice with a small test call and writes the default provider to the global config, shared with Kapi Desktop, whose first-open **Connect your AI** card offers the same detected sign-in as a one-click button. `kapi models list` shows it under *Detected*, alongside Ollama models and any cloud keys. Subscription use is window-limited: a heavy run that exhausts your Claude usage window holds back the remainder and reports when it resumes ("Claude subscription limit reached; resumes ~7pm"); the next `kapi up` picks up exactly the blocks still pending. For uninterrupted or CI runs use an API key instead: subscription auth is bound to your personal sign-in and its usage window, so **CI should always use a key** (a provider env var, or `kapi credentials add`). See [Ship gates & CI](/kapi/recipes/ship-gates-and-ci).
