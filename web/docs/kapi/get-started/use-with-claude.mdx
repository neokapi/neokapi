# Use with Claude

kapi and Claude connect in **two directions**. In one, you work in Claude and it drives kapi: the assistant writes and translates inside kapi's guardrails. In the other, kapi runs Claude: your local Claude Code sign-in becomes kapi's AI provider, so `kapi up` and `kapi translate` run on your Claude subscription with no API key. Start from what you have:

| You have… | Use |
|---|---|
| **Claude Pro or Max** (Claude Code installed) | Both directions. [Work in Claude](#work-in-claude) via the skill or MCP; run `kapi models setup` and [kapi runs Claude](#let-kapi-run-claude) on your subscription, no key. |
| **An API key** (Anthropic, OpenAI, Gemini) | `kapi models setup` finds keys already in your environment, or stores one in the OS keychain, and verifies it with a test call. |
| **Nothing, or offline** | A local model via [`kapi models ollama`](/kapi/recipes/choose-a-translation-provider), or Kapi Desktop's demo engine (illustrative output, no AI). |

## Work in Claude

You describe the outcome; Claude runs kapi. kapi supplies the guardrails (the faithful round-trip, voice profile, terminology, the check gates) and Claude does the writing inside them. All paths need `kapi` on your `PATH` ([installation](/kapi/get-started/installation)); no provider credential is required for attended work: Claude writes, kapi applies and checks, with no second model.

| You work in… | Use | How it drives kapi |
|---|---|---|
| **Chat** (Claude Code, plain-language prompts) | the **Agent Skill** (`SKILL.md`) | Claude runs `kapi` commands itself and loops until the gates pass |
| **IDE** (Claude Desktop, Cursor, Windsurf, VS Code) | the **MCP server** (`kapi mcp`) | the rules in `AGENTS.md` and `CLAUDE.md`, `context_read` for a file they do not cover, `context_note` for what it notices, and `check_file`; `--tools` adds [more sets](/reference/mcp#available-tools) |
| **CI** (no assistant in the loop) | the **CLI** directly | `kapi check` / `kapi check --ship` exit non-zero, failing the build |

<details>
<summary>Install the Agent Skill (Claude Code and any SKILL.md-aware tool)</summary>

**Claude Code**: the plugin bundles the skill plus two hooks:

```text
/plugin marketplace add neokapi/claude-plugins
/plugin install kapi@neokapi-plugins
```

The **Stop hook** runs the project gate (`kapi check --ship`) when Claude tries to finish and keeps it working while a gate fails; the **PreToolUse hook** denies hand-edits to generated translation targets, steering changes through the source. Both are fail-open outside a project, and both follow one [decision protocol](#the-hook-decision-protocol).

**Copilot, Cursor, Windsurf, VS Code, Codex**: `SKILL.md` is an open standard:

```bash
npx skills add neokapi/agent-skills --skill kapi     # add -a <tool> for a specific tool
npx skills update kapi                               # refresh later
```

</details>

<details>
<summary>Install the MCP server (Claude Desktop, Claude Code, Cursor, and the rest)</summary>

`kapi init` configures supported clients automatically. Use the following example for manual configuration or another compatible client.

Your client launches `kapi mcp` as a stdio subprocess. Claude Code and Cursor read the server list under `mcpServers`; VS Code reads it under `servers`. Claude Desktop uses `claude_desktop_config.json` with the same shape as Claude Code's:

```json
{
  "mcpServers": {
    "kapi": {
      "type": "stdio",
      "command": "kapi",
      "args": ["mcp", "--project", "kapi.yaml"]
    }
  }
}
```

`--project` names the project the server answers for, so it binds yours rather than whichever project sits above the directory your client started it in. The writing tools include `read_blocks`, `apply_edits` and `describe_format`, which read a file's blocks, write edits back with the file's structure and inline codes kept, and say what a format supports. For a project that declares target languages, `kapi init` adds `"--tools", "writing,translation"` to the arguments, so the agent also gets the translation tools beside the writing ones.

See [MCP server](/reference/mcp) for every client's configuration and the full tool list.

</details>

### The hook decision protocol {#the-hook-decision-protocol}

A kapi hook states its verdict as JSON on stdout and always exits `0`. The verdict travels on stdout rather than in the exit code: Claude Code reads a non-zero exit as a *broken hook*, so a denial carried that way would be downgraded to a hook error rather than enforced. `kapi check --ship` keeps its own gate exit code (`3`) when you run it yourself; the hook drives that gate without replacing it.

| What the hook found | On stdout | What happens |
|---|---|---|
| A gate fails / the file is a generated target | `{"decision":"block","reason":"…"}` (Stop) · `{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":"…"}}` (PreToolUse) | Claude keeps working, or the edit is refused. The `reason` names the findings, or the source and locale to change instead. |
| Nothing to report (gates pass, the file is not generated, or there is no kapi project) | nothing | The operation proceeds. |
| **The guard could not run at all** | `{"systemMessage":"…"}` plus the same warning on stderr, naming the hook | The operation proceeds: kapi hooks fail open, so a broken guard never blocks work. But the bypass is stated, because a guard that never ran must not look like a guard that passed. |

An unreadable, empty, or malformed hook payload; a session directory kapi cannot enter; a recipe that will not load because it needs a plugin you have not installed: each of those leaves the guard installed but inert. The notice says which hook, and what stopped it.

The wire shapes are Claude Code's, and Claude Code versions its own hook schema; kapi does not add a version of its own. What is stable here is the policy in the table: fail open, and report the bypass.

The workflow is the same for either integration: the agent writes to the rules in `CLAUDE.md` and `AGENTS.md`, asks `kapi context <path>` only for a file those rules do not cover, and runs `kapi check` on each file it changed. A [project](/kapi/get-started/first-project) says which voice and terms apply to each file. For example, ask: “Check `README.md` against our voice profile and fix the failing findings.”

As it works, the agent notes what the files do every time and what you change in its drafts, with the file and sentence each came from. Each note arrives as a **suggestion**: checks report it and none fails on it until you keep it. An agent that noted something ends its report with what its session suggested and the command that reviews it, `kapi context review --session <id>`. A note holds only in the files where the agent saw it until you widen it in review. See [Growing context](/kapi/context-decisions).

The project also states its rules where the assistant reads them first. `kapi init` writes a section into `CLAUDE.md`, the file Claude Code reads, and into `AGENTS.md`, which most other agents read: the voice, what to write and what not, and the `kapi check` line. A folder whose rules differ from the root's gets files of its own, so a rename kept for `help/` is stated in `help/CLAUDE.md`, and `api/CLAUDE.md` says the old name is correct there. kapi rewrites the section when the context changes and leaves the rest of each file as you wrote it; a `CLAUDE.md` that imports `@AGENTS.md` gets no section of its own. See [rules files for agents](/kapi/context#rules-files).

### What `kapi init` wires up {#what-kapi-init-wires-up}

`kapi init` also writes the configuration the agent itself reads, so an agent opened in the project finds kapi with nothing else installed:

| Agent | What it gets |
|---|---|
| **Claude Code** | `.mcp.json` with the `kapi` server, and the kapi skill in `.claude/skills/kapi/SKILL.md` |
| **Cursor** | `.cursor/mcp.json` with the `kapi` server |
| **VS Code** | `.vscode/mcp.json` with the `kapi` server |
| **Codex** | `.codex/config.toml` with the `kapi` server, read once you trust the repository |
| **Any SKILL.md-aware tool** | the kapi skill in `.agents/skills/kapi/SKILL.md` |

The skill explains how to read what applies to a file, note what it sees and what you change, check edits, and report the session. It gives CLI and MCP equivalents. For detailed guidance, `kapi help` lists topics and `kapi help <topic>` prints the selected guide from your installed binary.

Claude Code is wired every time. The others are wired when the project already keeps their directory, so `kapi init` adds no directory for an editor you do not use. Choose for yourself with `--agents`:

```bash
kapi init --agents claude-code,cursor   # exactly these
kapi init --agents all                  # every agent kapi knows
kapi init --agents none                 # write no agent configuration
```

`--agents` chooses the configuration each agent reads. The rules files are
written for every agent; `kapi init --no-rules-files` leaves them out.

Everything it writes is inside the project, and it writes nothing but a command: no shell, no environment, no credential. An entry called `kapi` that you wrote or changed is left exactly as it is; an entry exactly as `kapi init` wrote it follows the recipe, so adding target languages and running `kapi init` again gives the agent the translation tools. Running `kapi init` again is also how a project you created earlier gets the same wiring. A skill directory an earlier kapi filled with reference files is cleared of the files kapi wrote there, and any file of yours in it stays.

Claude Code asks you to approve a project MCP server the first time you open the project, so review `.mcp.json` before you say yes, the way you would any file a repository ships.

## Let kapi run Claude

For unattended runs (`kapi up` across every locale, `kapi translate` without you in the loop) kapi needs a provider of its own. If Claude Code is signed in on your machine, that provider can be your Claude subscription:

```bash
kapi models setup     # detects the Claude Code CLI ("uses your Claude subscription"): one confirm, no key
```

Setup verifies the choice with a small test call and writes the default provider to the global config, shared with Kapi Desktop, whose first-open **Connect your AI** card offers the same detected sign-in as a one-click button. `kapi models list` shows it under *Detected*, alongside Ollama models and any cloud keys. Subscription use is window-limited: a heavy run that exhausts your Claude usage window parks the remainder and reports when it resumes ("Claude subscription limit reached; resumes ~7pm"); the next `kapi up` picks up exactly the blocks still pending. For uninterrupted or CI runs use an API key instead: subscription auth is bound to your personal sign-in and its usage window, so **CI should always use a key** (a provider env var, or `kapi credentials add`). See [Ship gates & CI](/kapi/recipes/ship-gates-and-ci).
