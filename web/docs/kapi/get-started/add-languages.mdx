# Add languages

Add a target language, and kapi keeps it caught up with the source: it reuses earlier translations, translates the rest, and holds back for review what needs a person. A language that is behind is pending work and never breaks a build.

In Kapi Desktop you add a language in **Project Settings** and click **Translate** on the project's Overview. On the command line you declare it in the recipe and run `kapi up`. An assistant can do either for you.

In the installed kapi, declaring a target language in the recipe also adds the language commands (`translate`, `pseudo-translate`, `memory`) to `kapi --help`. Before that, `kapi help languages` lists them.

1. **Add the locales.** In **Project Settings**, add the target languages you translate into (for example `fr`, `de`). On a project in one language, **Review** in the sidebar opens the same choice, and once you save the first target it holds the review queue.

2. **Translate.** On the project's **Overview**, the language standing shows one row per locale against the ship gate. Targets the content memory holds an exact match for are already filled: the app recycles them when it reads the files, and the Overview counts them, such as **12 blocks recycled**. **Plan…** previews the rest first: the blocks left to recycle, the AI work, a token estimate, nothing written. Then click the button that names the work, such as **Translate 12 blocks**; kapi runs the default flow over every locale that is short of its gate, looping until each scope ships or a gate holds it back for a person.
3. **Review.** Click a ship-gate cell to open the **Review** queue for that locale: inspect each translation, edit if needed, approve or reject. Approvals raise the approved coverage that an `{ established: … }` gate measures; the recipe spells the approved rung `established`.

<TabItem value="cli" label="CLI">

Declare the locales in the recipe (or pass `--target-locale` at `kapi init` time):

```yaml title="kapi.yaml"
defaults:
  source_language: en
  target_languages: [fr, de]
collections:
  - path: "src/locales/en/*.json"
    target: "src/locales/{lang}"
```

The `target:` says where a translated file goes. `kapi add` writes it for you
(`kapi add "src/locales/en/*.json" --target "src/locales/{lang}"`), including on
a pattern `kapi init` already added without one. It refuses a target that lands
back inside the pattern it comes from, which would make the collection re-track
its own output as source, and a pattern whose entry already declares a
different target, which you change in the recipe.

A file belongs to the first entry in the recipe whose pattern matches it, so a
target applies to the files its entry claims. `kapi add` counts those, names
each other file with the entry that claims it, and refuses a pattern whose
every file an earlier entry claims.

Then catch up, inspect, and gate:

```bash
kapi up                  # run the default flow; stop where a gate holds content back
kapi status              # per-locale coverage and ship-gate standing (never fails)
kapi status --review     # the worklist: translated blocks awaiting a person
kapi check --ship        # enforce the gates: the pre-release bar, exit 3 when unmet
```

`kapi up` needs a translation provider for LLM translation; see [Choose a translation model](/kapi/recipes/choose-a-translation-provider). Approve reviewed blocks with a `decide` operation through `kapi apply`; see [Review & approve](/kapi/recipes/review-and-approve).

## How the gate works

Each translation climbs a ladder (draft, translated, approved). A **ship gate** is a set of coverage thresholds over that ladder, such as `{ translated: 100, established: 80 }`.
