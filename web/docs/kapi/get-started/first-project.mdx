# Your first project

A project is a committed recipe (`kapi.yaml`) that says which files count as
content, plus the wiring that lets the coding agents in your repository reach
kapi. Set it up once and every surface works the same project: the desktop app,
your assistant, and the CLI.

**Your project starts with an empty context**, and that is the normal state on
day one. It has no terms, no approved wording and no house rules, because the
words a project cares about are the ones it turns out to use. The context fills
as you and your agents work: an agent records what it notices, you keep what
is right, and from then on `kapi check` holds new writing to it.

That context lives in your workspace on this machine, one store per project,
and every checkout, worktree and clone of the project reads the same one. The
files in the repository say what counts as content and what governs it; what
the project has learned is held beside them.

A new project is source-only, so the loop below is about your own writing.
[Add languages](/kapi/get-started/add-languages) when you want them.

## 1. Create the project

<Tabs groupId="surface" queryString>
<TabItem value="desktop" label="Desktop" default>

Install [Kapi Desktop](/kapi/get-started/installation#install-kapi-desktop) and
open it. On first open, the **Connect your AI** card offers whatever it detects
(a Claude Code sign-in that
[uses your Claude subscription](/kapi/get-started/use-with-claude#let-kapi-run-claude)
with no key, a local Ollama model, or a stored API key) in one click; or skip
and use the demo engine.

1. **Create the project.** On the home screen, click **New Project**, name it,
   and pick a source language. Or click **KapiMart** under *sample projects* to
   explore a realistic, pre-seeded project first: content collections, a bound
   voice profile and terms, five target languages, and a stocked content memory.
2. **Add content.** In the **Project** view, add a pattern that matches your
   source files (for example `docs/**/*.md`). Kapi lists the matched files and
   the detected format, grouped into a collection.
3. **Read where it stands.** The project home says where the project is on two
   axes: **Content** (what has been read in, what changed on disk, what is
   missing) and **Governance** (the voice profile in force, the terms bound,
   when it last converged). Below, the **point map** gives one row per point the
   recipe declares. Bind a voice profile and set the default point under
   **Project Settings**; the **Context** hub then shows what applies at any file.
4. **Bring it up to date.** **Bring up to date** runs the project's default flow
   until every gated scope is shippable or parked for a person, the desktop form
   of `kapi up`. For a source-only project that means the checks. Anything a
   machine cannot decide lands in the **Review** queue; see
   [Review & approve](/kapi/recipes/review-and-approve).

<TabItem value="agent" label="Agent (Claude)">

With the [Kapi skill or MCP server](/kapi/get-started/use-with-claude)
connected, ask for the project:

> Set kapi up for this project.

Claude runs `kapi init`, which proposes the content collections from the files
in the tree, and reads the list back to you to adjust. What it writes is
committed: a recipe saying which files count as content, and the wiring that
lets the next session reach kapi. From there your prompts stay short; "check
this is on brand" needs no flags, because the project carries what the check
reads.

</TabItem>
<TabItem value="cli" label="CLI">

[Install the CLI](/kapi/get-started/installation), then from your content
directory:

```bash
kapi init                      # write kapi.yaml with the content it finds, and wire your agents
```

`kapi init` reads the files in the directory, honouring `.gitignore` and
skipping dependency and build directories, and names what it chose and every
file it writes:

```
Initialized kapi project "acme-docs"
  recipe: /path/to/acme-docs/kapi.yaml
  collections (proposed from the files here; edit the recipe to change them):
    README.md     markdown, 1 file
    docs/**/*.md  markdown, 12 files
  mcp:    .mcp.json (created: kapi mcp --project kapi.yaml)
  skill:  .claude/skills/kapi (created: 1 file)
```

The collections are the files kapi reads as content: documents grouped by
directory, a file at the root on its own, and i18n catalogs where a known
framework layout or a file named for the source language marks them. Each one
carries a comment in the recipe saying what it matched. Change them freely;
`kapi add "<pattern>"` adds another. Running `kapi init` again leaves them as
they are and prints any content no collection reads yet, with the lines to add.

The last two lines are the wiring: an MCP entry that starts `kapi mcp` for this
project, and a short kapi skill that tells an agent what to do and leaves the
rest to `kapi help <topic>`. Once the project binds a voice, `kapi init` adds a
short section to `CLAUDE.md` pointing an assistant at it, and
`kapi voice pointer` writes that section on its own. Choose the agents with
`--agents`, or opt out with `--agents none`. See
[what `kapi init` wires up](/kapi/get-started/use-with-claude#what-kapi-init-wires-up).

For a known stack, `kapi init --preset react-i18next` (or `nextjs`, `vue-i18n`,
…) writes its catalog layout even before the files exist;
`kapi init --list-presets` lists them.

The recipe is plain YAML. `defaults:` carries what applies to every collection,
and `collections:` names the content:

```yaml title="kapi.yaml"
version: v1
id: prj_fbqdv5uoovvpkaarpy5vnexhaq
name: acme-docs
defaults:
  source_language: en

collections:
  # README.md: Markdown, at the root
  - path: README.md
    format: markdown
  # docs/: 12 Markdown files
  - path: "docs/**/*.md"
    format: markdown
```

`id:` is the project's identity. It survives a rename, a move and a clone, and
it is what joins two checkouts of one repository to one context. Keep it.

Commit the recipe and the agent wiring. `.kapi/` is a cache for this checkout,
where [everything derived from your files](/kapi/project-store) goes; `kapi init`
writes an ignore rule that keeps all of it out of version control, and deleting
it costs a re-read of your files.

What the project learns goes elsewhere. The terms, the voice profiles, the
wording you approve and the record of who approved it are held in your
workspace, keyed on the `id:` above, so a rule you keep on one branch holds
on every branch and in every worktree. See
[Context portability](/kapi/context-portability) for moving that context to
another machine or handing it to somebody else.

Every kapi command run anywhere in the tree finds the project by walking up,
like git. See the [project file reference](/reference/project-file) for the full
schema. When you want AI-backed steps, `kapi models setup` detects what you
already have and confirms it as the default
([Use with Claude](/kapi/get-started/use-with-claude)).

## 2. Work as you normally would

The next step is the work itself. Open your assistant in the repository and give
it an ordinary writing task: fix a page, draft a section, rename a feature
across the docs. Claude Code asks you to approve the project MCP server the
first time, so review `.mcp.json` the way you would any file a repository ships.

While it works, the agent reads what applies at each file it touches and
**records what it notices**: how you spell your own product, which word you use
where two would do, and every wording you change in its draft. Each of those is
recorded as a **suggestion** with the file it came from. It ends its report with
what the session recorded.

Nothing it records is in force. Checks report suggestions and fail on none of
them, so an agent can keep recording while you work without any risk of
stopping a build.

## 3. Read what it recorded

```bash
kapi context log
```

On a project where nothing has happened yet:

```
No context operations are recorded here yet.
```

After a session:

```
#3  2026-09-21T19:22:20Z  agent claude-code/s4980103f5148  observe  term "use", not "utilise"  [suggested]
  seen in docs/guide.md: "We utilise the widget to configure your account."
  Every other page in docs/ says "use".
#2  2026-09-21T19:22:20Z  agent claude-code/s4980103f5148  observe  "The product is written \"Acme Widget\" in headings and \"the widget\" in running text."  [suggested]
  seen in docs/guide.md: "We utilise the widget to configure your account."
```

Every line carries who recorded it, what it is about, where it stands, and the
file and sentence it was seen in. `--status suggested` narrows the list to what
is waiting for you, and `--session <id>` to one agent run.

In Kapi Desktop the same log is the **Recorded** feed: on the home screen across
every project, and in a project's **Context** hub for that project alone. It
groups by session, and the evidence sits on the card, because a decision taken
without it is a guess.

## 4. Keep what is right

```bash
kapi context keep 3
```

```
#4  2026-09-21T19:23:01Z  person  keep  of #3
  written to the project's terms store
```

Keeping establishes the rule and puts it in the project's terms store, where
every checkout reads it and `kapi context log` holds the decision beside the
evidence it rested on. Change it as you keep it with `--use` and `--severity`,
or set it aside with `kapi context drop 3`. Either way the record stays in the log, so the
same suggestion is recognisable the next time somebody makes it.

Deciding is yours. An agent observes and records corrections, and it has no
verb for keeping, dropping, reverting or widening. [Growing context](/kapi/context-decisions) covers the whole set of
verbs, including undoing a whole agent session in one command.

## 5. Check

```bash
kapi check docs/guide.md
```

Before you kept anything, the suggestion read as a note and the check passed:

```
  severity  rule              location                                    message
  NEUTRAL   voice.vocabulary  docs/guide.md:getting-started/next-steps/p  Proposed rule about "utilise", not yet confirmed: Every other page in docs/ says "use".
                                                                          ↳ Use "use" instead
  NEUTRAL   voice.vocabulary  docs/guide.md:getting-started/p             Proposed rule about "utilise", not yet confirmed: Every other page in docs/ says "use".
                                                                          ↳ Use "use" instead

PASS configured checks: score 100/100 · 2 finding(s) (0 critical, 0 major, 0 minor)
  Coverage: 2 analyzer runs completed.
  Context: docs/guide.md; voice none (project); terms none loaded
```

The `Context:` line says what the check was evaluated against: the voice profile
in force at that file, and whether the project's terms store had anything to
say. After keeping, the same word is an established rule and bites at the severity it
carries:

```
  severity  rule              location                                    message
  MAJOR     voice.vocabulary  docs/guide.md:getting-started/next-steps/p  Forbidden term "utilise" found in terms
                                                                          ↳ Use "use" instead
  MAJOR     voice.vocabulary  docs/guide.md:getting-started/p             Forbidden term "utilise" found in terms
                                                                          ↳ Use "use" instead

PASS configured checks: score 90/100 · 2 finding(s) (0 critical, 2 major, 0 minor)
  Coverage: 2 analyzer runs completed.
  Context: docs/guide.md; voice none (project); terms loaded
```

Run `kapi check` with no path to check the whole project, and `kapi check
--ship` to enforce release policy. It exits `3` when a gate is unmet, which is
what makes it a CI step: see [Ship gates & CI](/kapi/recipes/ship-gates-and-ci).

Repeat steps 2 to 5 as you work. Each session adds to what the project holds,
and a person decided every part of it.
