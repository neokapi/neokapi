# Your first project

By the end of this page, a folder of documents spells one word the same way
everywhere, and every edit is checked for it. You set the rule once, and Kapi
Desktop, the CLI and your assistant all check it.

A project is a `kapi.yaml` file in your repository. It lists the files kapi
reads, and `kapi init` adds the files your coding assistant needs to use kapi.
Your first project has one language. You can add more later.

The examples use `acme-docs`, a git repository with a `README.md` and five
Markdown files under `docs/`. Most of the files have *email*, but two places
have *e-mail*.

Each step has a tab for Kapi Desktop and one for the CLI. Step 1 also has one
for an assistant. Kapi Desktop and the CLI use the same project, so you can
switch at any step. The tab you pick stays selected for the rest of the page.

[Install the CLI](/kapi/get-started/installation), then from the folder:

```text
$ kapi init
Initialized kapi project "acme-docs"
  recipe: /path/to/acme-docs/kapi.yaml
  collections (proposed from the files here; edit the recipe to change them):
    README.md     markdown, 1 file
    docs/**/*.md  markdown, 5 files
  mcp:    .mcp.json (created: kapi mcp --project kapi.yaml)
  skill:  .claude/skills/kapi (created: 1 file)
  rules:  AGENTS.md (created)
  rules:  CLAUDE.md (created)
```

`kapi init` looks at the files in the folder. It skips files listed in
`.gitignore` and dependency and build folders. It groups the files it will
read into collections: documents by folder, a file at the root on its own, and
string catalogs for apps. To add more files, run `kapi add "<pattern>"`. If
you run `kapi init` again, it keeps your collections and lists any files they
don't cover yet. For a known app setup, `kapi init --preset react-i18next`
(or `nextjs`, `vue-i18n`, …) sets up the catalog files before they exist. Run
`kapi init --list-presets` to see them all.

The last four lines set up Claude Code. Step 6 explains them.

`kapi.yaml` is plain YAML:

```yaml title="kapi.yaml"
version: v1
# This project's stable identity. It survives a rename, a move and a clone,
# and everything kapi records about the project is keyed on it. Keep it.
id: prj_fyvo35str3o4bv3aty766bj6w4
name: acme-docs
defaults:
  source_language: en

# Collections are the files kapi reads as content. kapi init proposed these
# from the files it found. Edit them freely; 'kapi add <pattern>' adds more.
collections:
  # README.md: Markdown, at the root
  - path: README.md
    format: markdown
  # docs/: 5 Markdown files
  - path: "docs/**/*.md"
    format: markdown
```

Keep the `id:` line. It ties every clone and worktree of the repository to the
same rules. Commit `kapi.yaml` and the assistant files. `kapi init` keeps the
`.kapi/` folder out of git. It holds caches and your personal settings, plus
any text you chose to hide from AI models. If you delete it, that hidden text
is lost. See [The project store](/kapi/project-store) and the
[project file reference](/reference/project-file).

Like git, kapi finds the project from any folder inside it.

## 2. See what applies

<Tabs groupId="surface" queryString>
<TabItem value="desktop" label="Desktop" default>

The project opens on its **Overview**. It shows the same things as
`kapi look`: how many files, blocks, rules and findings the project has,
suggested rules under **Suggestions**, and the **Files** list.

A new project has no rules yet. kapi looks at how your files are already
written and suggests rules from that, without using an AI model. In
`acme-docs`, **Suggestions** lists *email*, used in 5 of 7 places.
The two uses of *e-mail* show up as findings, but they don't fail anything
yet. Click `docs/guide.md` under **Files** to open it in the **Reader**, where
each finding is marked on its words.

## 3. Decide what becomes a rule

<Tabs groupId="surface" queryString>
<TabItem value="desktop" label="Desktop" default>

Click **Decide** on the Overview. For each suggestion you see which forms your
files use, how many blocks use each one, what keeping it does, and a sentence
where it was found. **Keep** (`k`) makes the marked form a rule. **Not a
rule** (`n`) removes the suggestion. **Later** (`l`) keeps it as a suggestion
for now.

<ThemedImage
  alt="Decide asking which spelling the project should use, with the options, what keeping one does, and the sentence it was seen in"
  sources={{
    light: "/img/desktop/light/decide.png",
    dark: "/img/desktop/dark/decide.png",
  }}
/>

When you keep a suggestion, kapi saves it as a rule in the project's terms
store and adds it to its section of `CLAUDE.md` and `AGENTS.md`. Your
assistant reads the rule there the next time it starts. In this video you
decide suggestions in the KapiMart sample, then see the rules an assistant
gets for one file, including the one you kept:

<ThemedVideo
  sources={{
    light: "/video/kapi/kapi-desktop-context-light.webm",
    dark: "/video/kapi/kapi-desktop-context-dark.webm",
  }}
/>

Only a person can keep or drop a suggestion. See
[Growing context](/kapi/context-decisions) and [Review your assistant's
suggestions](/kapi/desktop/recipes/review-your-assistants-suggestions).

</TabItem>
<TabItem value="cli" label="CLI">

Run `kapi rules`. For each suggestion, it shows where the suggestion comes from
and what keeping it does:

```text
$ kapi rules
[1/1] Which spelling should the project use?  #0rbnyk4bjm
  * 1) email  5 blocks in 4 files
    2) e-mail  2 blocks in 1 file
    3) e mail  0 blocks in 0 files
    4) Other…
  If you keep "email": the other 2 forms become findings in 2 blocks. Applies to the whole project.
  Seen "Create a workspace, then invite your team by e-mail address." in docs/guide.md

Decide with: kapi rules --keep <id>, --drop <id> or --later <id>
```

Type your answer: `k` keeps the marked form, a number picks another form, `n`
means it isn't a rule, and `l` leaves it for later. A suggestion you leave for
later stays a suggestion. In a script or CI, where nobody can type an answer,
`kapi rules` only lists the questions. Answer one by its id, for example
`kapi rules --keep 0rbnyk4bjm`.

When you keep a suggestion, kapi saves it as a rule in the project's terms
store and adds it to its section of `CLAUDE.md` and `AGENTS.md`. Your
assistant reads the rule there the next time it starts:

```
Say this, not that:
- email, not "e mail" or "e-mail"
```

Add `--advisory` to keep a rule that only reports and never fails a check.
`kapi rules list` lists the project's rules, and `kapi rules drop <id>` removes
one. Only a person can keep or drop a suggestion. See
[Growing context](/kapi/context-decisions).

</TabItem>
</Tabs>

## 4. Check

<Tabs groupId="surface" queryString>
<TabItem value="desktop" label="Desktop" default>

Before you kept the rule, *e-mail* was only reported. Now each use of it
fails. Click **Run on everything** on the Overview to check the whole project.
Click the findings count to see each finding with its rule and where it is,
like a test report. In the **Reader**, each finding is marked on its words,
and the rule is shown under the block.

<ThemedImage
  alt="A file in the Reader with a finding marked on its words, the rule's wording under the block and Fix beside it"
  sources={{
    light: "/img/desktop/light/reader.png",
    dark: "/img/desktop/dark/reader.png",
  }}
/>

To fail a build on the same findings, run `kapi check` in CI. See
[Ship gates & CI](/kapi/recipes/ship-gates-and-ci).

</TabItem>
<TabItem value="cli" label="CLI">

Before you kept the rule, `kapi check` passed. Now it fails on each use of
*e-mail*:

```text
$ kapi check docs/guide.md
  outcome  rule              location                                      message
  FAILS    terms.vocabulary  docs/guide.md:getting-started/next-steps/p#2  Forbidden term "e-mail" found
                                                                           ↳ Use "email" instead
  FAILS    terms.vocabulary  docs/guide.md:getting-started/p               Forbidden term "e-mail" found
                                                                           ↳ Use "email" instead

FAIL configured checks: 2 failing, 0 reported · score 50/100
  Coverage: 2 analyzer runs completed.
  Context: docs/guide.md; voice none (project); terms loaded
Error: quality gate failed
```

The `Context:` line shows which voice profile and terms were used. Run
`kapi check` with no file name to check the whole project, or
`kapi check --ship` to check the release rules. Both end with exit code `3`
when something fails, so you can use them as a CI step. See
[Ship gates & CI](/kapi/recipes/ship-gates-and-ci).

</TabItem>
</Tabs>

## 5. Fix

<Tabs groupId="surface" queryString>
<TabItem value="desktop" label="Desktop" default>

In the **Reader**, click **Fix** next to a finding to replace the words with
the rule's wording. **Fix 2 in this file** fixes every finding in the file at
once. The rest of the file stays exactly as it was.

Some findings have no **Fix** button: findings about tone or style, and
findings on words that contain a link or other formatting, which a plain
replacement would remove. Edit those words yourself.

</TabItem>
<TabItem value="cli" label="CLI">

Run `kapi fix`. It replaces each failing word with the rule's wording, then
checks the changed files again:

```text
$ kapi fix
2 fixed in 1 file
  docs/guide.md  2 fixed: e-mail → email, e-mail → email
kapi check: no failing findings
```

The rest of each file stays exactly as it was. To see the changes without
making them, run `kapi fix --dry-run`. Findings about tone or style, and
findings on words that contain a link or a placeholder, can't be fixed
automatically. `kapi fix` lists them so you can rewrite them yourself.

</TabItem>
</Tabs>

## 6. Put an assistant on it

<Tabs groupId="surface" queryString>
<TabItem value="desktop" label="Desktop" default>

Open **Project Settings** and go to **Assistants**. Each assistant has a row.
`kapi init` already set up Claude Code, so its row says **Connected**. Click
**Connect** on another row to set up that assistant, the same as
`kapi connect`. **Show what it reads** shows the rules kapi adds to
`AGENTS.md` and `CLAUDE.md`, and the rules for any file you pick, the same as
`kapi context <path>`.

See [Connect an assistant](/kapi/desktop/recipes/connect-an-assistant).

</TabItem>
<TabItem value="cli" label="CLI">

`kapi connect` adds what an assistant needs to follow your rules: a rules
section in `AGENTS.md` and `CLAUDE.md`, an MCP server entry for this project,
and the kapi skill. `kapi init` already did this for Claude Code, so nothing
changes here:

```text
$ kapi connect
Claude Code   connected · rules, MCP server, skill
  .mcp.json            kept
  .claude/skills/kapi  kept
  Edit hook            pending: in Claude Code, /plugin marketplace add neokapi/claude-plugins, then /plugin install kapi@neokapi-plugins
  Stop hook            pending: in Claude Code, /plugin marketplace add neokapi/claude-plugins, then /plugin install kapi@neokapi-plugins
Cursor        not connected: no .cursor/ folder here (kapi connect cursor adds it)
VS Code       not connected: no .vscode/ folder here (kapi connect vscode adds it)
Codex         not connected: no .codex/ folder here (kapi connect codex adds it)

Project
  kapi.yaml            kept
  AGENTS.md            kept
  CLAUDE.md            kept

See what an assistant reads for a file: kapi context <path> --explain
```

</TabItem>
</Tabs>

Now give the assistant a normal writing task. It reads the rules when it
starts. Before it writes a file the rules section doesn't cover, it runs
`kapi context <path>`, and it runs `kapi check` on each file it changes. The
first time, Claude Code asks you to approve the project's MCP server, so check
`.mcp.json` as you would any file in a repository.

While it works, the assistant also suggests rules: patterns it sees in your
files, and wording you change in its drafts. These show up in `kapi rules`,
and you decide on them as in step 3. See [Use with Claude](/kapi/get-started/use-with-claude).

## 7. Share the rules

<Tabs groupId="surface" queryString>
<TabItem value="desktop" label="Desktop" default>

Your rules are saved on this computer, linked to the project's `id:`, so every
copy of the project here uses the same rules. Open **Project Settings** and go
to **Share** to see who else can use them. Every project starts **On this
Mac**. **With your team** shares the rules through git, a shared folder or an
S3 bucket. Click **Change** to pick where, and **Sync now** to send your rules
and get your team's.

<ThemedImage
  alt="The Share page with three rungs, On this Mac marked Current, With your team and the managed workspace"
  sources={{
    light: "/img/desktop/light/share.png",
    dark: "/img/desktop/dark/share.png",
  }}
/>

Commit the change to `kapi.yaml`, so everyone's copy shares through the same
place. See [Share context with your
team](/kapi/desktop/recipes/share-context-with-your-team).

</TabItem>
<TabItem value="cli" label="CLI">

Your rules are saved on this computer, linked to the project's `id:`, so every
copy of the project here uses the same rules. Run `kapi share` to share them
with your team. In a git repository with a remote, `--via git` stores them in
git, separate from your branches:

```text
$ kapi share --via git
kapi.yaml  updated
With your team · through git (origin refs/kapi/context)
  pushed 6 changes · pulled none · last sync just now
```

Commit the change to `kapi.yaml`, so everyone's copy shares through the same
place. After that, run `kapi share` to send your rules and get your team's. See [Sharing context](/kapi/context-portability).

</TabItem>
</Tabs>
