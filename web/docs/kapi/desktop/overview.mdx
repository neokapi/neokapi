# Kapi Desktop

kapi holds the context for one project. Kapi Desktop is where a person reads and
edits it.

That context is what the project goes by: the voice profile in force, the terms
that apply, the checks that must pass, and where each of those holds. The
[kapi CLI](/kapi/cli) and the [MCP server](/reference/mcp) are how scripts and
assistants ask about it. The desktop is how the person who governs the project
asks the same questions, and makes the decisions that answer them.

The three are peers. A CLI verb, an MCP tool and a desktop panel resolve through
one host layer, so they answer the same question with the same data, and a
conformance suite holds them to it.

## What the app opens to

The app opens on your **workspace**: every project kapi has run in on this
machine, whichever surface ran it. Set a repository up from a terminal and it is
on the list when you next look, with no step in the app. Each project shows its
name, its identity, when it was last active, and the folders it has been seen
in. Two worktrees or two clones of one repository are one project with two
folders beneath it, because they share an identity and one context.

A folder that has gone away is marked missing rather than dropped: the project
and its context are unaffected, and the row still says where the files were. A
project with no copy on this machine, one you have only ever opened elsewhere,
opens on its context alone. **Open a Project** is there for a folder kapi has
never run in, and opening it adds it to the list.

Removing a project from the workspace is something you ask for. The confirmation
names the file that will be deleted and the folders that will not, and nothing
else in the app removes a project as a consequence of anything.

A project reopens as a tab, and the tabs you had last time come back. A
project's home says where it stands, on two axes:

- **Content.** What has been read into the project, what has changed on disk
  since, and what is missing.
- **Governance.** The voice profile in force, the terms store bound, when the
  project last converged, and whether it is in sync with the venue it declares.

Below that, a **point map** gives one row per point the recipe declares, with
the collections that sit there and the voice bound to them. Most projects are
one point, and show one row.

**Bring up to date** is the action beneath. It runs the project's default flow
until every gated scope ships or parks, and **Plan…** beside it shows the
pending work, the leverage available from content memory, and a token estimate
before anything runs.

## Context

The **Context** hub is where the graph is legible:

- **Explorer** answers by location and by content. Ask what applies at a file,
  or search for a word and see the terms, the prior wording, and where each is
  used.
- **Agent View** shows the context an agent receives for a file you pick: the
  point it resolves to, the voice in force, the terms that apply, and the body
  the agent reads, word for word. It is the same answer `kapi context <path>`
  prints.
- **Recorded** is what you and the agents working in the project have noticed,
  proposed and decided. See [Working beside an
  agent](#working-beside-an-agent).
- **Voice** renders the profile that actually governs a point: tone, style
  rules, vocabulary with severities, examples, and the overrides that apply.
  Where a binding was skipped because its window had closed, the page says so
  rather than quietly resolving past it. Editing writes the same YAML in your
  working tree that you would edit in git.
- **Terms** is the concept store: the words the project has decided on, their
  status, and their translations.
- **Content Memory** is the record of prior wording, searchable with its
  provenance intact.

## Working beside an agent

Keep the app open while an agent works in one of your projects. The agent runs
in its own process, through the kapi CLI or its MCP server, and what it records
about terms, voice and wording arrives here within a second or two. Nothing
connects the two: both read and write the same project context on this machine.

**Recorded** on the home screen carries every project's work; the same section
inside a project's Context hub carries that project's. Each entry says what was
done, who did it and on which machine, what the rule or the wording was, and
the evidence behind it: the file, the unit and the sentence it was seen in. The
evidence is on the card for anything waiting on you, because it is what the
decision rests on.

A proposal advises from the moment it is recorded and binds only once you
confirm it. Until then it is reported by a check as a proposal and fails
nothing, so an agent's suggestion never stops your work.

For each entry waiting on you:

- **Confirm** writes the rule into the project's terms, voice profile or
  content memory, where `git diff` shows it and every check reads it.
- **Edit** changes what the rule says to write instead, and how hard it bites,
  before you accept it. Minor and neutral report a violation; major and
  critical fail a check.
- **Discard** rejects it. It stops advising at once.
- **Undo** takes a confirmed rule back out, and **Undo session** does that for
  everything one agent session recorded. The confirmation names how many
  operations go.

The keys are the review session's: `j` and `k` move, `a` confirms, `r`
discards, `e` edits.

A confirmed rule can be **widened**: out to every project in your workspace, or
past one axis of the point it was learned at, so it answers more widely in its
own project. You see where it would reach before you accept. The count of files
it would touch is not part of that; run a check afterwards to see what it
reports.

A count beside a project says how many decisions are waiting there. It is
absent when there are none. Deciding writes into the project's files, so it
needs a copy of the project on this machine: a project you have only ever
opened elsewhere can be read here and not decided on.

## Collections and formats

A project's content is grouped into named collections. Each collection is a set
of patterns, and the desktop shows the real files they match beside the format
kapi detected for each.

Opening a file previews it the way the engine reads it: the rendered document,
the blocks it parsed, and, where a format carries them, the structure (roles and
reading order) and the layout (page-scaled bounding boxes). Media files render
as themselves, an image with its recognized text boxed, or an audio or video
player with the recognized cues as a synced track. Formats that need an engine
plugin offer to install it on first use. The
[format reference](/formats) lists what kapi reads.

## Checks

Checks are the tests for prose. A finding names the rule that fired and the
point it is scoped to, and clicking it lands on Context there, with the rule in
view. Fixing what a check found is the loop the app is built around: see the
rule, see the wording it governs, change one or the other.

## And in every language

A project that declares target languages gets the multilingual half. Per-language
coverage appears on the collections it applies to, the **Review** queue takes
whatever the loop could not carry to the ship gate, and inspection puts source
and target side by side with their findings, to approve, reject, or sign off.

A project that declares none is complete as it is.

## Install

On macOS, the cask installs the app and bundles the `kapi` CLI:

```bash
brew install --cask neokapi/tap/kapi
```

See [Installation](/kapi/get-started/installation#beta-channel) for the release
channels.

For the Windows installer and the macOS DMG / Linux tarball builds, see
[Installation](/kapi/get-started/installation#install-kapi-desktop).

## The project file

Everything you configure is written to a portable `kapi.yaml` recipe. Commit it
to git to share with your team, reopen it in Kapi Desktop, or run it from the
command line:

```bash
kapi up -p kapi.yaml
```
