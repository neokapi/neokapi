# A guided tour

Kapi Desktop is where you read what your projects write by and decide about
what your assistants noticed. This tour walks each surface in the order the
app presents them, the context first and the files after. For what the app is
and how to install it, see the [overview](/kapi/desktop/overview).

## What's new

The app opens on **Your context**: counts for the projects, the rules in force,
the terms, the suggestions advising and what needs you, then **What's new**,
with a row for each project where an assistant noticed something since you last
looked. A row carries the assistant's mark and a chip for each kind of thing it
noticed. **Review** on a row opens the project on its own What's new.

There, a list holds one line per item, and the pane beside it shows the item
you select: the sentence it was seen in, the file, and the assistant that
noticed it. **Needs you** comes first, with two suggestions that disagree
about one word. **Suggested**, **Established** and, when content moves away
from a rule, **Drift** follow. `j` and `k` move the selection. **Keep** (`a`),
**Change** (`c`) and **Drop** (`d`) decide about a suggestion, and the
selection moves on to the next one. A disagreement shows its two sides next
to each other, and **Choose this side** settles it. **Apply more widely** puts
a rule in force across the project or the workspace.

## Ask

**Ask** asks by file or by word. Give it a file and it shows what applies
there. Search a word and it returns the terms that cover it, the prior wording
that used it, and where.

## What your assistant reads

**Assistant** shows what an assistant working in the project is told.
**Connected assistants** has a row for Claude Code, Cursor, VS Code, Codex and
Claude Desktop. A filled dot and **Connected** mark an assistant that is
connected, and **Connect** on any other row writes the files `kapi init`
writes. Below the rows are two tabs. **Rules files** shows the section kapi
writes into `AGENTS.md` and `CLAUDE.md`, which an assistant reads as it
starts. **The brief for a file** is the full answer an assistant gets for the
file you choose, the same text `kapi context <path>` prints. See [Connect an
assistant](/kapi/desktop/recipes/connect-an-assistant).

## Voice, terms and content memory

**Voice** shows the voice profile that applies, as it applies: tone, style
rules, pattern rules, examples, and the language, channel and persona
adjustments. When dated guidance has lapsed, the page says which and why.
Editing writes the YAML in your working tree, the same file a reviewer reads in
a pull request.

**Terms** lists the words the project decided on, one concept per row: the
term, its status, and how many languages it has terms in. The search at the top
of the list narrows it as you type. Select a concept and the pane beside the
list shows its definition, the forms it retires with what to write instead,
its terms language by language, where it came from, and the concepts it relates
to. **Relate** links it to another concept.

**Content Memory** lists the approved wording one pair per row: the source
sentence, and the language it was translated into. The filter bar at the top of
the list searches on Enter, and **Filters** narrows the list by language, target
language, project, the kinds of name an entry holds, the import it came from,
or whether it carries inline codes; each choice shows as a token you can also
type, such as `target:fr-FR`. **Find similar** looks up wording like a sentence
you type instead, with the names in it marked, and lists the matches best first
with their scores. Select a pair to read both sides in full, with inline
formatting kept as tags, the file the entry came from and the unit it was
approved for. **Pair** and **All languages** above it switch between the pair
and every language the entry holds, beside **Edit**, **Mark entities** and
**Delete**. The box at the start of a row marks its entry, and with entries
marked, **Delete** and **Mark entities** act on all of them. **Add entry** sits
at the top of the page.

## History

**History** lists what was recorded in the project, one session per row, newest
first: who worked, when, and how many operations the session holds. Select a
session to see its operations beside the list. A suggestion still waiting for a
decision keeps **Keep**, **Edit** and **Drop** on its row, with the sentence it
was seen in behind a click. **Reset to before this session**, above the
operations, goes back to how the context stood before the session started. The
reset is recorded too, and **Take this reset back** on it brings back what it
set aside.

## Share

**Share** shows how far the project's context reaches, as a stepper over
three rungs. The rung the project stands on is filled, and the card under the
stepper describes the rung you select, with the one action that moves the
project on. **On this Mac** is where every project starts: every clone and
worktree on this machine reads the same context, and the card names your
workspace folder. **Shared with your team** is a git ref, a folder or an S3
bucket that every machine syncs. Its card offers **Set up sharing** until a
place is named, then shows the place and the last sync, with **Sync now** and
**Change**. See [Share context with your
team](/kapi/desktop/recipes/share-context-with-your-team).

:::note[Works with Bowrain]
The third rung is **Managed on Bowrain**. Its card reads "Bowrain holds every
project's context in one workspace, with roles, review and a record of who
decided what, and runs the project's loop on the server." and offers **About
Bowrain**, which opens [How Bowrain and kapi fit
together](https://bowrain.cloud/docs/getting-started/kapi-vs-bowrain). A
project whose recipe declares a `bowrain:` block reaches a Bowrain server,
and the rung is then the current one. Its card reads "The recipe connects this
project to a Bowrain server.", names the server and the workspace, for example
`app.bowrain.cloud` and `acme`, and offers **Open the project**. The
**kapi-bowrain** plugin (`brew install neokapi/tap/bowrain-cli`) carries the
transport.
:::

## Where the project stands

The **Project** section answers "where is this" on two axes before it offers
to do anything.

**Content** is the blocks the project's files hold, and what is missing. **Governance** is the voice profile in force, the
terms that apply, when the project last converged, and whether it is in sync
with the venue it declares.

Beneath, **Where content sits** gives one row for each part of the project the
recipe declares, with the collections there and the voice that applies to them.
A project with one voice for everything is one row.

**Bring up to date** runs the project's default flow until every gated scope
ships or parks. **Plan…** beside it is the pre-flight: the pending work, the
leverage available from content memory, and a token estimate, before anything
runs.

Three counts above the button separate the run's work from a person's.
**Blocks to translate** are what the run drafts. **Waiting for review** opens
Review. **Languages held back** lists each collection language that does not
ship yet and what holds it back: a ship gate not yet met, a failing check, or a
source that changed after approval. The app reads the project's files when the
project opens and again when they change, so no step reads them in by hand.

## Collections and formats

A project's content is grouped into named collections: documentation, store
copy, contracts, templates. Each is a set of patterns, and the home shows one
card per collection with the real files matched beside the format kapi detected.

Opening a file previews it the way the engine reads it. A **Preview** of the
rendered document, a **Blocks** list, and, where the format carries them, a
**Structure** view of roles and reading order and a **Layout** view of
page-scaled bounding boxes. Media renders as itself: an image with its
recognized text boxed, or an audio or video player with the recognized cues as a
synced subtitle track. Opening a file whose format needs an engine plugin offers
to install it there and then. The [format reference](/formats) lists
what kapi reads.

Click a block in the Preview and choose **Edit** to change it in place: its
source, or a translation the project carries for it. Formatting and placeholders
stay as chips you type around, and saving writes the file through its format,
leaving every other byte as it was.

## Checks

Checks are tests for prose, and the panel reads like a test report. A finding
names the rule that fired and where it applies, and clicking it opens Context
there with the rule in view.

That click is the loop: see what was found, see the rule that found it, then
change the wording or change the rule. A finding whose rule names the wording to
use instead offers **Apply fix**, which puts that wording in place of the flagged
words in the file. When the flagged words have formatting among them, such as a
link or bold text, there is no Apply fix, because plain wording in their place
would drop the formatting; open the document and edit them there. When the text
changed after the run, the panel shows it as it is now and asks before applying
the fix. Collections can be re-run individually as you work.

## Flows and the toolbox

The **Toolbox** holds the flows a project runs over its content: a plain AI
translation, a translation followed by quality checks, a pseudo-translation for
testing. Each is a named sequence of steps saved beside the project and shared
through version control. Open one to edit its pipeline, and run it through the
runner with live per-file progress.

The tool browser beside it is a reference. It says what each tool does, what it
consumes and produces, and the command line that runs it.

## Settings, providers, and plugins

Settings has four tabs: **General** for appearance, **AI Models** for the
providers and models kapi runs with (keys stay in your OS keychain, never in the
project file), **Plugins** for the formats and tools that extend it, and
**Locales**. Project Settings carries the recipe itself: the languages, the
voice and terms each part of the project uses, and
the default flow.

Plugins install from the registry in one click, and the formats and tools they
add appear in the project immediately. The
[manage plugins](/kapi/desktop/recipes/manage-plugins) recipe walks it step by
step.

## And in every language

A project that declares target languages gets the multilingual half. Per-language
coverage appears on the collections it applies to, and the **Review** queue takes
whatever the loop could not carry to its ship gate. Inspection puts source and
target side by side with their findings, to edit, approve, or reject,
keyboard-first, with an optional AI pre-review to triage a long queue. See
[Review & approve](/kapi/recipes/review-and-approve).

A project that declares no target languages is complete without this, and
Review stays quiet.
