# MCP server

kapi exposes its format-aware content engine as an
[MCP](https://modelcontextprotocol.io/) (Model Context Protocol) server. An
assistant connected to it can read the content inside a `.docx`, a JSON catalog
or a Markdown file, ask what the project's own context says about a phrase,
edit the content, verify it against the project's checks, and write it back
byte-for-byte, through structured tool calls rather than by guessing at the
file's bytes.

For the agent-skills path (Claude Code calling the `kapi` CLI), see
[Use the Kapi Agent Skills](/kapi/get-started/use-with-claude). The two can be
used together.

:::info Generated from the server
The tables on this page are generated by connecting to a real `kapi mcp` server
and asking it for its tools and its resources. A CI drift gate fails the build
if they stop matching the binary, so nothing here can describe a tool the server
does not answer to, or an address it does not serve.
:::

## Quick Start

Start the MCP server:

```bash
kapi mcp
```

This launches a JSON-RPC server on stdio. You don't run it manually; your AI
tool starts it as a subprocess. With no flags it serves the
[writing set](#available-tools); `--tools` names others.

## Setup

### Claude Desktop

Add to your Claude Desktop config (`~/Library/Application Support/Claude/claude_desktop_config.json` on macOS, `%APPDATA%\Claude\claude_desktop_config.json` on Windows):

```json
{
  "mcpServers": {
    "kapi": {
      "command": "kapi",
      "args": ["mcp"]
    }
  }
}
```

Restart Claude Desktop. Kapi tools will appear in the tool picker.

## Available tools

`kapi mcp` serves tools in named sets. An assistant reads every tool description
it is offered and chooses among them, so a server offers the sets its work
needs. `--tools` takes a comma-separated list, and a name that is not a set is
refused with the list of sets:

```bash
kapi mcp                               # the writing set
kapi mcp --tools writing,translation   # writing, plus the loop that fills target languages
kapi mcp --tools all                   # every set
```

**writing** is the default: the `context://` resources and these
<McpToolCount surface="writing" /> tools, which ask what applies, record what
the assistant notices, read and edit a file's blocks with its structure kept,
and check what it changed.

**content** works on content directly:

**translation** runs the loop that fills target languages:

`apply_edits` from the writing set, which records a pre-review:

<McpToolList surface="review" />

Project scoping applies on top. Started inside a kapi project (discovered by a
git-style upward walk, exactly as the CLI discovers it), the tool set is
narrowed to the sources the recipe declares and the project's first target
language becomes the default for the translating tools.

### Tools from installed plugins

An installed plugin adds its own tools to this surface. `kapi mcp` starts each
plugin's server once per session and passes calls through, so the tools a plugin
brings answer on the same connection that serves the loop verbs. Configure one
MCP server, not one per plugin.

A plugin contributes the tools its manifest declares. A plugin that is not
installed adds nothing, one that fails to start is left off with a note on
stderr while the rest of the surface keeps working, and a plugin tool whose name
kapi already uses is skipped so the kapi tool keeps the name.

### Widening the surface

Two flags on `kapi mcp` add tools no set holds, for debugging and for callers
who really are assembling a pipeline by hand:

- `kapi mcp --all-tools` adds every CLI-visible processing tool, plus the
  listing verbs: <McpToolNames surface="all-tools" />.
- `kapi mcp --all-flows` adds the flow-running verbs:
  <McpToolNames surface="all-flows" />.
- `kapi mcp --all` serves every set and adds both.

Two tools are withheld from every surface, including the widened ones:
`external-command` and `script` run arbitrary commands and JavaScript, which is
a different class of decision from "show me every tool". Both remain available
through `kapi exec`.

## Available resources

Retrieval comes in two shapes, a tool and a resource. Asking what a word
means is a call with arguments, so it is the `context_search` tool. Asking what
applies at a location is reading something that already exists at an address,
so it is a **resource**:

<McpResourceList />

The two addresses are one primitive. A path answers *what applies here*; a
profile name answers the same question for a caller with no file in hand (an
ad-hoc run, or a starter pack). The markdown is the brief a writer reads: the
voice, one list of words to use and to avoid, and what has been suggested but
not yet established, as [`kapi context <path>`](/kapi/context#what-applies-here)
prints it. The JSON adds the point the location resolved to, the full voice
guide, the terms, the governance windows and the provenance.

The `suggestions` list is reported apart from everything in force. Each entry
carries its status, `suggested` or `contested` (with `contested_by` naming the
other side), the rule or note it states, who suggested it, in which session and
the evidence behind it, with the operation id a person keeps it by. A check
reports every suggestion and fails on none of them.

The server offers these addresses as resource templates, and many clients list
no resources from a template, so an assistant there cannot discover them on its
own. [`context_read`](#context_read) returns exactly the same text as a tool,
the server's instructions name the address, and `kapi context <path>` prints
the same text for an assistant that can run a shell command.

**The rendering is a property of the read.** `?format=json`
returns the same answer as `application/json` (the document `kapi context <path>
--json` prints) and everything else returns `text/markdown`. An unrecognised
format is refused rather than answered with prose a program cannot parse.

```
context://docs/guide.md                # markdown, for a model to read
context://docs/guide.md?format=json    # the same answer, for a program
context://profile/marketing            # a named profile, no location needed
```

The CLI half is [`kapi context <path>`](/reference/commands/context), which
calls the same host function and prints the same markdown. A conformance test
holds the two surfaces to the same answer.

## Example conversations

### "How many words need translating?"

> How many translatable words are in `src/locales/en.json`?

The assistant calls `stats` with the file path and returns a structured answer
with word, block, character, and segment counts.

### "What do we call this here?"

> Is "sign-in" the term we use, and how do we say it in French?

The assistant calls `context_search`. One question reaches every store the
project binds (its terms, its content memory, its voice profile) and the
answer says what the project calls the thing, whether it is discouraged and
what to say instead, and any wording already approved. Asking before writing is
cheaper than learning the same fact from a failing check afterwards.

Every answer carries `notes`, and the first of them says whether the context,
the terms or the decisions moved since this session last read them. What a
person must act on, such as a checkout whose context nobody has imported, is also in
`attention`, and it is the part of the notes the text answer shows. The
comparison is against what the project last observed of its server, held on
disk, so it costs a small file read and no round trip, and it reports rather
than resolves: an assistant told the terms moved asks again before continuing,
because the wording it had settled on was chosen against a context that has
since changed.

### "Show me the content of this file"

> Show me the translatable strings in `messages.json`

The assistant calls `read_blocks` with the document's path and returns a page
of blocks: each block's reference and revision, its text with inline codes as
`<x id="…"/>` placeholders, the codes and their attributes, and the operations
the block accepts.

### "Edit the content, then check it"

> Tighten the intro paragraph in `report.docx`, keeping it on brand

The assistant reads the blocks with `read_blocks`, rewrites the text itself
(no second model), and sends a change set through `apply_edits`: one
`replace_text` or `set_content` operation per block, addressed by the `ref` the
read reported and guarded by its `rev`. kapi writes it through the format's
writer, keeping the document's structure and inline codes, then the assistant
calls `check_file` to confirm the gate passes, looping until it does.

### "Catch the project up"

> What translation work is outstanding, and how much would it cost?

The assistant calls `up_plan`, a dry run reporting, per collection and locale,
the units missing a target, the content-memory leverage, the remaining AI work
and a rough token estimate. Nothing is written and no provider is called. `up`
then does the work: re-extract what drifted, reuse the content memory, translate
the rest, run the project's checks, and loop until every gated scope is
shippable or parks for a human.

### "Review this translation"

> Show me the French units waiting for review, and pre-review them for me

The assistant calls `review_queue`, reads each candidate with `review_block`
using the `ref` its row carries, and records a pre-review through
`apply_edits`: a `decide` operation at that `ref`, with `if_match` set to the
`rev` `review_block` returned, outcome `advise`, a score from 0 to 100 and its
reasons. The pre-review is bound to the wording the assistant read and
recorded under the identity `agent/<client>`, so a later edit drops it. It
decides nothing: the unit stays in the queue until a person approves or
rejects it, and an assistant's `establish` is refused.

`review_queue` returns one queue across the project's languages. Each row
carries `language` and, when that language is the project's source, `isSource:
true` and a `status` on the authoring ladder; `languages` counts the pending
units per language, so an assistant can narrow with the `language` argument to
one that has work. `review_block` reads a source-language unit the same way it
reads a translation, from the source file, and returns its point and
neighbourhood with no target half.

## Tool reference

### context_read

Read what applies when writing one file, before changing it: the voice, the
words to use and to avoid, and what has been suggested but not yet established.
It returns exactly the text the `context://<path>` resource returns, for a
client that lists no resources from a template. `path` is project-relative, or
`profile/<name>` for a named profile.

<McpToolParams name="context_read" />

### context_search

A word somebody has suggested a rule or a note about comes back under
`suggestions`, apart from the terms in force.

<McpToolParams name="context_search" />

### context_observe

Record an observation about project wording. Use `text` for a note, or `term`
and `instead_of` for a suggested term rule: kapi adds the
spacing, hyphen and case variants of a compound, so `Quickcast` instead of
`Quick cast` also avoids `Quick-cast`, `QuickCast` and `quickcast`. A term rule
needs `path`. The result is a **suggestion**: every check reports it, and none
fails on it until a person keeps it with `kapi context keep <id>`.

<McpToolParams name="context_observe" />

### context_correct

Record that the person changed some wording: what was there, what replaced it,
and where. `suggest` also records the rule the change implies, as a
suggestion.

<McpToolParams name="context_correct" />

### context_withdraw

Take back something this session recorded wrongly, such as a correction entered
backwards, by the `operation` id its call returned. An assistant withdraws only
its own session's suggestions. A person must handle established rules and suggestions from other sessions.

<McpToolParams name="context_withdraw" />

### context_session_summary

What this session recorded and what became of it, counted as `observed`,
`corrected`, `suggested`, `contested`, `established`, `withdrawn`, `dropped`
and `reverted`, with the sentence to end a task report on. The report ends with
the `kapi context keep --session <id>` command a person keeps the session's
suggestions with.

<McpToolParams name="context_session_summary" />

Keeping, dropping, reverting and widening are reserved for people through the
CLI or desktop and are excluded from the MCP tools. See
[Growing context](/kapi/context-decisions).

### read_blocks

Read a document's blocks, a page at a time. Each block carries `ref`, the
reference an operation names (`doc`, `block` and, for a translation,
`edition`), and `rev`, the revision of the edition the read showed, which an
operation sends as `if_match`. `text` holds the content with inline codes as
`<x id="…"/>` placeholders, which an edit keeps; `codes` names what each
placeholder stands for, and `structures` lists the branches of a plural or a
select with the `path` that reaches each. Pass `next` back as `cursor` for the
following page. Inside a project, `doc` is a path relative to the project's
root, and the file of a translation reads that edition of its source. The
format is the one the project's recipe binds to the file, or the one kapi
detects, and `apply_edits` writes the file in the same format. A source code
file whose comments kapi checks is refused as `unsupported` with the
capability `comment`: edit a comment in the file itself, then run
`check_file` on it.

<McpToolParams name="read_blocks" />

### apply_edits

The write verb. `apply_edits` takes a `kapi.change/v1` change set, the contract
every kapi surface sends ([E-09](/contribute/architecture/engine/e-09-the-change-contract)),
plus the per-call `project`.

<McpToolParams name="apply_edits" />

| Operation | What it changes |
| --- | --- |
| `set_content` | an edition's whole text, keeping its placeholders; with `if_match: "absent"` and an `edition`, it creates that translation |
| `replace_text` | part of the text, named by `find`, by `start` and `end`, or by `range` |
| `remove_edition` | drops a translation, where the format keeps translations in one file |
| `insert_block` | adds a key to a JSON, YAML or ARB catalog, with its text in each language |
| `delete_block` | removes a key from such a catalog and from each translation's file |
| `decide` | a pre-review: outcome `advise`, with a score and reasons |

`describe_format` lists what each format supports; an operation the format
refuses is refused as `unsupported` and writes nothing.

```json
{
  "note": "Name the handbook",
  "ops": [
    {
      "op": "replace_text",
      "at": { "doc": "docs/guide.html", "block": "p" },
      "if_match": "r:3f9a1c0e7b2d4a55",
      "edits": [{ "find": "shop guide", "text": "handbook" }]
    }
  ]
}
```

A refused change set writes nothing. An edition that changed since it was
read is refused as `stale`, and the refusal carries its current revision and
text, so the assistant can rebase without another read. An edit that drops,
invents or unbalances an inline code, or flattens a plural or select, is
refused as `guard`. A reference that names no block is `not_found`, and a block
the format reads as not translatable, such as a code block, is `unsupported`.
Every other operation of a refused change set reports `not_applied`, and the
result is an error. The status `partial` is an error too: some of the change
set landed. Either a write stopped after some files were written, and `docs`
names them, or the content was written and a decision recorded after it was
refused, and that operation carries the error. The assistant reads the
documents again before it sends more. `mode: "preview"` computes the result
and a diff per document and writes nothing. A source edit lists the
translations it made stale under `invalidates`.

`apply_edits` sends every change set as the calling agent in the server's
session; a change set has no field that names its sender. Writing a term, a
content-memory pair or a field of `kapi.yaml` is a person's decision, so a
change set holding a `term`, `memory` or `recipe` operation is refused as
`not_permitted` and writes nothing. The assistant records a term rule as a
suggestion with `context_observe`, or with `context_correct` for wording it
changed, and a person keeps it. A review decision is a person's too: an
assistant's `decide` takes only the outcome `advise`, with the score it gives.
A person sends the same operations with `kapi apply` in a terminal.

## How it works

Kapi MCP uses the same machinery as the CLI commands: the format registry for
detection, the executor for flow orchestration, and the same built-in tools.
The MCP server exposes them as typed, discoverable tools over the
[Model Context Protocol](https://modelcontextprotocol.io/) stdio transport.

No server process, ports, or authentication needed. Your AI tool launches
`kapi mcp` as a child process, communicates over stdin/stdout, and shuts it
down when the session ends.

:::note
Most tools here are rule-based and need no API key: `context_search`,
`check_text`, `check_file`, `voice_check`, `voice_rewrite`, `stats`,
`read_blocks`, `apply_edits`, `describe_format`, the context write tools and
the review tools all run offline. The
ones that reach a language model (`translate`, and `up` when there is work the
content memory cannot cover) need a provider credential, which they read from
the same credential store the CLI uses (`kapi credentials add`).
:::
